# CLAUDE.md

Guidance for Claude Code (claude.ai/code) working in this repository.

## Project Overview

`claudio` is a Claude Code profile **and** account manager. A *profile* bundles project-level configuration (MCP servers, permissions, hooks, skills, commands, subagents, instructions); activating one symlinks it into the current directory — a venv for Claude Code. An *account* is an isolated `CLAUDE_CONFIG_DIR`, so its own login. A profile says what Claude has; an account says who Claude is. The axes are independent: any profile runs under any account.

## Language & Conventions

- Single POSIX `sh` script (`claudio`) — no bash-isms (no `local`, no `[[ ]]`, no arrays, no `printf -v`, no process substitution). The Homebrew formula depends on `jq`, on `python@3.12` and on `gabrielbelli/tap/claude-statusline`. The renderer is a real dependency of the formula and not of the program: recording works with no renderer at all — a shim with nothing to forward to prints zero bytes, which is a legitimate silent sensor — but the docs tell people to write `statusline=claude-statusline`, and a package that leaves them to go and find it is a package that does the last step badly. It is named by its tap rather than bare, because a top-level `Formula/` makes this repository itself tappable and a bare name does not resolve there. Python is **declared rather than assumed** for the reason this project always gives: relying on the system interpreter is a guess about every machine, and the failure it produces is the quiet one — `claudio run` still launches and stream A simply stops being recorded. claudio guards every optional dependency itself — Docker only for MCP mode, `jq` for mixed mode and for **usage recording** — and a missing `jq` costs you a sample, never a command.
- **No build step, but no longer one file.** `claudio usage` and `claudio recv` are stdlib Python shipping beside the script, so the install is `make install` (`$PREFIX/bin/claudio` plus `$PREFIX/libexec/claudio/`) and `Formula/claudio.rb` calls that same target rather than listing files of its own — two lists of what claudio consists of is how a new module reaches a checkout and not a package. The old documented install, `sudo install -m 755 claudio /usr/local/bin/claudio`, copied the script alone: `_tool_path` then fell through to a bare name that was never on `$PATH`, both verbs failed, and because `claudio recv` is what stream A is exported *to*, the visible symptom was an empty ledger rather than an error. `test.sh` runs the real `Makefile` into a temporary `DESTDIR`, runs the installed verbs out of the result with a **decoy of each name at the front of `$PATH`**, and derives the file list from the tree so a module added tomorrow is checked without anyone remembering to add it. It also pins the Homebrew shape specifically — a symlink into the tree — because `_self_path` resolving symlinks is the only reason a brew shim finds `../libexec`, and a `dirname $0` regression would look perfect in a checkout. `make check` is the documented way to run the suites and is pinned to name **both shells and both Python suites**: a `check` that quietly dropped the `dash` line would keep printing a green wall while every no-bash-ism regression walked through it. **And it is pinned not to weaken them**, which is a correction: the reconciler's suite self-skipped 44 of its 192 test functions — 918 assertions — printed a banner saying the run was not evidence about the engine, and exited 0, so `make check` exited 0 too, on the one command this project documents as the release gate. A banner on stdout is nothing that CI, `&&` chains or Make read. The ruling moved into the suite rather than into a flag in the `Makefile` — every caller inherits it, including a human running the file directly, and the `Makefile` stays free of the dependency's name, which its own boundary test requires. `--allow-skips` is the escape hatch, it says out loud what it accepted, and the guard checks **both places** the opt-out fits: the `check:` body *and* the default of `SERVER_SUITE_ARGS`, because the first draft checked the body alone and a `SERVER_SUITE_ARGS ?= --allow-skips` fifty lines above left the suite green. **`make uninstall` is scoped to a stage.** It ended in `rmdir` on `$PREFIX/bin` and `$PREFIX/libexec`, justified as removing exactly what `install -d` created — but `install -d` does not create a directory that already exists, and at uninstall time nothing can tell the two apart, so `make install PREFIX="$HOME/.local"` followed by `make uninstall` deleted a directory the user made and put on their `$PATH`. The orphan-in-a-package problem only exists in a `DESTDIR` stage, which is built empty, so that is the only place the pair runs. The old test pair could not see it: one asserted the removal as correct and the other only ever exercised a **non-empty** directory, which `rmdir` refuses anyway.
- **`receiver=` is one key read by both halves, and it was one key read by one half.** `claudio`'s `_recv_cmd` has honoured it since the spawn work landed; nothing under `usage/` read it at all. So a machine with a working `receiver=` had `claudio run` start that receiver while `claudio usage doctor` reported one *missing* at the bundled path — a WARN, and every WARN sets a non-zero exit — and `collect start` would have launched the other one. `config.receiver()` is now the Python half's answer, global-conf-only for the same reason the shipping keys are: a path in a `claudio.conf` inside a repository someone else wrote must never name the program this machine executes. The conf reader **moved** into `config.py` rather than being copied, because `ship` already imports `collector` and the third option was a second five-line parser the two halves would have to keep agreeing about; the test asserts `ship.read_conf is config.read_conf`, the same identity assertion `tail.file_identity` has. And `receiver_missing()` names the key **and the file** when the key is what chose the path: "receiver missing at <path>" is a true sentence that sends the reader to the tree, where the file is exactly where it ships and nothing is wrong.
- Tests: **`bash test.sh` *and* `dash test.sh` — both, every time.** `/bin/sh` on macOS is bash 3.2, so `sh test.sh` alone proves nothing and hides exactly the portability bugs the no-bash-isms rule exists to catch. Each run prints the shell it exercised `claudio` under; check that line says what you expect. The suite runs in a temp directory with stubbed `docker` and `git`, and reads the replay goldens from `fixtures/` next to it. Mixed-mode, JSON-validity and **every usage-recording** test self-skips without `jq` — the recorder cannot work without it — so **the test count is machine-dependent**, and substantially so now. Never quote a total in the docs; it has drifted every time someone has. Run the suite without `jq` on `$PATH` as well when you touch the recorder: the promise is that a missing `jq` costs a sample and never a command, and the only way to know is to try it.
- British English in all prose.
- **The docs are pinned by tests, in both directions.** `_usage` and the dispatch `case` are extracted from the script and compared as sets, so a command can be added to neither without the other; and the `CLAUDIO_*` variables the script actually reads are compared against the tables in `claudio`'s header comment, `readme.md` and `CLAUDE.md`, which must all name the same set. Both guards derive their lists rather than hardcoding them — a hardcoded list is a fourth place to forget.

## Architecture

**One map, one lister, one prologue.** `CONFIG_MAP` pairs each profile item with its target path (`mcp.json:.mcp.json`, …) and drives `use`, `clean`, `init` and `show`, so item-specific logic is never repeated. `_dirnames` is the single lister behind `_profiles` and `_accounts`, which used to disagree about hidden directories. `_run_prelude` is the entire shared prologue of `run` and `env`: optional leading profile, shared options, active-profile fallback, account resolution and validation. `default` calls `_parse_run_opts` directly instead — it takes no profile and launches nothing. Sharing the parser has one sharp edge worth knowing: `default` therefore *accepts* `--no-telemetry` and `--` and then does nothing with either, because it only ever reads `RUN_ACCOUNT` and `RUN_TAGS`. `_usage` scopes the shared-options block to run/env for that reason, and a test pins the scoping — telemetry is a config-file setting, so there is nothing for `default` to write. **`env` has the same edge, one verb further in:** it shares the parser *and* sits under the `Options for run/env:` header, but it launches nothing, so the tokens after `--` are parsed and dropped, exit 0, no diagnostic. The fix taken was to scope the `--` line to `run` in `_usage`, pinned by its own assertion, rather than to make `cmd_env` reject leftovers: the reword is needed either way (erroring does not make "passed to claude" true under a `run/env` header), while erroring would newly fail two shapes that exit 0 today — `claudio env p -- x` and `claudio env p stray` — and break anyone whose shell profile has `eval "$(claudio env …)"` carrying a stray argument. The leftover check is a legitimate follow-up, cheap when wanted: `cmd_default` already has the two-line pattern and `cmd_use`'s message is already pinned.

**MCP.** Docker MCP Toolkit by default: a profile is Docker-mode iff it carries an `mcp.docker` marker, and its `mcp.json` is then *generated* as a gateway runner, with server management delegated to Docker rather than reimplemented. Mixed mode covers what Docker isn't fit for — `mcp.extra.json` holds remote HTTP/SSE and bespoke servers, merged next to the gateway entry with `jq`. Pure-Docker and manual profiles never invoke `jq`; if extras exist and `jq` is missing, it warns and writes gateway-only rather than failing.

**The status line is a shim, registered against accounts.** What Claude Code runs is `claudio statusline --shim`, never the renderer directly: it reads the payload Claude Code pipes in, records a plan-usage sample, and forwards the identical bytes to the command named by `statusline=` (global conf only — it names a command on this machine). It is registered in `<account>/settings.json` because an account **is** a `CLAUDE_CONFIG_DIR`, so that file is the *user-level* settings for every session run under it: recording then follows the identity into any directory, with or without a profile, which is the right axis because the quota is account-wide. **Profiles must never write one** — a profile's `settings.json` is symlinked to `.claude/settings.json`, which is *project* level and beats the account's, so a profile-written status line would shadow the shim and silently stop recording in exactly the projects the user works in most.

Writing into an account directory *is* writing into a `CLAUDE_CONFIG_DIR`, which departs from the `.claudio-relogin` precedent (claudio's own file rather than an edit to Claude Code's JSON). The distinction is that the never-write rule is about `~/.claude`, whose layout is Claude Code's to change; an account directory is one claudio created and manages, and `settings.json` is the only file in it that can make recording work at all. Nothing writes into `~/.claude`, and a static test still asserts it.

**Every account is born wired**, whether or not `logging=` is set and whether or not a renderer is configured, so enabling either later is a conf edit rather than a re-setup — and a shim with nothing to do prints zero bytes, which is indistinguishable from having no status line. `_statusline_apply` therefore lost its "return 1 if `statusline=` is unset" guard, which was the whole reason it existed at profile level.

**The registered shim names the entry point, never the resolved target, and Homebrew is why.** `_statusline_shim_cmd` used `_self_path`, which follows symlinks — correct for `_brew_ctx` and `_tool_path`, wrong here, because `<prefix>/bin/claudio` is a symlink into `Cellar/claudio/<version>/bin/claudio` and `brew upgrade` **deletes that directory**. The command written into an account's `settings.json` is stored, so it outlives the path it names: reproduced in a simulated prefix, the registered line became `sh: …/Cellar/claudio/0.1.0/bin/claudio: No such file or directory`, exit 127 — Claude Code draws nothing and plan-usage recording stops for good. And it is invisible on the surface built to show exactly this drift, because `_settings_has_shim` matches `statusline --shim` **without** the path in front of it, which it must, since the path differs per install. So `_statusline_entry_path` resolves the *directory* (`pwd -P`, which also collapses the `bin/..` a prefix introduces) and leaves the final component alone, with `_self_path` as the fallback. Pinned twice: the stored command must name the link and must not contain `Cellar`, and then the Cellar is swapped out underneath and the stored command is executed — a path assertion alone would pass for a link pointing nowhere.

**Two source lists, because there are two questions.** `_statusline_account_sources` answers "is this account already spoken for" — managed policy and that account's own `settings.json`, and deliberately nothing else: `$USER_SETTINGS` is not read by Claude Code at all when `CLAUDE_CONFIG_DIR` is set, the other accounts would mean the first wired one stops every later one from ever being wired, and the project files in cwd say nothing about an account used in every directory. `_statusline_sources` answers "what is in effect *here*" and is cwd-aware — managed, the two project files, then the **resolved** account's `settings.json` (or `$USER_SETTINGS` when no account resolves). Resolved, not globbed: a glob reports the first account in glob order, which is a confident answer about an account this directory may never use.

Detection is `grep '"statusLine"'`, not `jq`: the only action on a hit is to refuse, so a false positive costs a message while a missing dependency must never cost the user their status line. `_settings_has_shim` is the same grep for `statusline --shim`, matched without the path in front because that changes with where claudio is installed; it is what makes drift visible in `account list` and in the status report. `jq` is used only to *name* the command in a conflict report, because `"command"` also appears under `hooks` and `mcpServers` and a `sed` would confidently print the wrong program. Writing JSON without `jq` is why `_blank_settings_json` takes an optional extra member: regenerating the whole document is the only way to add a key, so the blank and the with-a-status-line form must come from one function. For the same reason `--set` **refuses** a `settings.json` claudio did not write, and prints the exact block to paste — with one exception that makes the retrofit useful at all: a file byte-identical to the blank plus a status line calling the **currently configured renderer** is one claudio wrote before the shim existed, and is upgraded in place. The shim forwards to that same renderer, so the line is unchanged and recording starts; one byte different and it is someone's edit again. Byte-compared, not parsed, for the same reason as everything else here.

**The shim is dispatched from the top of the file, and that is load-bearing, not a style violation.** It runs on every render, several times a second. A POSIX shell parses and executes a script file incrementally, so exiting from an early `if` never reads the other ~4 000 lines: medians of 60 runs with recording off and no renderer configured, `dash` 2 763 µs here against 9 084 µs from the dispatch table (bare shell spawn 2 461 µs); `bash` 6 133 µs against 16 353 µs (floor 5 308 µs). **Re-measured at 4 285 lines** — the earlier figures (dash 2 493/7 669, bash 6 166/14 451) were taken at ~2 600 and are replaced rather than quietly corrected; the early-exit and floor columns are unchanged within noise and only the table column moved, which is the shape the argument predicts, since what is being paid for is parsing the rest of the file. Tidying it down into `cmd_statusline` breaks nothing — it just costs ~6 ms/~10 ms per render forever, invisibly — so `test.sh` pins it twice, with an elapsed-time assertion and a static line-number assertion that names the cause. The same measurement is why `_no_slash` now **assigns `$_ns`** instead of printing: two `$( )` captures were ~1 ms of the ~1.2 ms the block spent reaching itself. Recording-off is the path optimised for: three config keys in one pass over the files, stdin untouched, no `jq`, and `exec` rather than wait. Recording-on falls through to the table, which is fine because it forks `jq` anyway — and so does a render that has found the receiver missing, which is the same trade made for the same reason: the spawn is the cold path by construction, so it is allowed to read the rest of the file.

**`_u_conf` is `_logging_resolve`'s rule, implemented twice on purpose.** `logging`, `usage_dir` and `account.<name>.logging` layer exactly as `otel` did, inversion included, but `_telemetry_conf` costs up to four `$( )` captures and the shim cannot pay that on every render — the same trade `_stamp_read` already makes. `_u_conf`/`_u_conf_file` are fork-free (`while read` in this shell, no pipeline), and they live in the early block because that is where the off-path needs them. They read **three keys in one traversal**, because the shim needs `logging`, the `usage` it replaces and `usage_dir` on every render — the receiver's pidfile lives in `usage_dir`, so the supervisor needs it too — and reading them one at a time would open every config file three times. That is why the early return per key became `_u_conf_next` blanking a resolved key's *name*: with three keys resolving at different depths there is no single layer at which to stop, and an empty name is what tells the shared reader not to look for that key again. `_u_record` no longer resolves `usage_dir` itself; it reads what the early block resolved, and an empty value is the single answer to both "unset" and "inside `~/.claude`, which claudio refuses to squat in". The two must agree; the `logging` precedence tests mirror the `otel` ones case for case so that changing one rule without the other fails. One thing the shim's copy deliberately does *not* do is print: a status line renders, it never diagnoses, so the deprecation notice is `claudio run`'s to give and a mode claudio does not know reads as off rather than as a guess.

**Anything that *reports* whether recording is on must resolve the account first.** `_statusline_wire_footer` and `_statusline_status` both called `_telemetry_conf usage "$(_active_profile)" ""` — no account — so with a global logging setting and `account.personal.logging=none` they told the one user who had deliberately switched an identity off that recording was on, contradicting the guarantee the key is sold on. `_statusline_recording` is now the single answer: it takes the account when the caller knows it (`--set <name>`) and otherwise resolves the one this directory would run under, the same way `_statusline_sources` does. Both shapes are pinned.

**The receiver for stream A is spawned on demand and supervised by the status line, and every part of that is a refusal of something.** `usage/recv/otlp-recv` is not a container and not a launchd/systemd unit: `claudio run` starts it before `exec claude`, the shim keeps it alive, and it exits by itself when the work stops. The service was rejected on three settled arguments — its flush argument was measured false (see `usage/cu/collector.py`), its coverage argument was near-empty because `_build_env` writes the OTLP variables only into the environment of the `exec`ed claude, so stream A does not exist outside claudio-launched sessions, and `launchctl`/`systemctl` cannot be stubbed in a hermetic suite. claudio's half is `_recv_*`, and five decisions carry it:

- **The gate is the environment, not the config.** `cmd_run` tests the variables `_build_env` has *just exported into this shell* (`CLAUDE_CODE_ENABLE_TELEMETRY`, and `_recv_target` on the endpoint), and the shim tests the ones it inherited from claude. Both are reading the export that is actually happening rather than re-resolving `otel=` a second time, where two resolutions could disagree; and for the shim it is also free, which a second layered pass over three config files would not be. It costs one honest limitation, stated rather than hidden: if Claude Code ever stops passing its environment to the status line command, the shim stops supervising and the next `claudio run` is what brings the receiver back. `--no-telemetry` is tested by `cmd_run` **above** the environment test, because an inherited `CLAUDE_CODE_ENABLE_TELEMETRY=1` would otherwise outlive the one flag whose whole job is to silence a single run.
- **http/json to a loopback endpoint, or nothing at all.** Those are now claudio's own defaults, so `otel=1` alone reaches the receiver; they were `grpc` and 4317, the Docker collector's shape, which meant the documented opt-in turned telemetry on, started nothing and exported to a closed port — silent loss as the feature's normal behaviour. A **remote** endpoint stays silent on the run path: claudio cannot know whether something is listening on an endpoint it did not choose, and `claudio usage doctor` prints the two lines to change. A **loopback** endpoint in a protocol this receiver cannot speak is the one mismatch that can only be a local mistake, so that one is named on stderr.
- **Nothing waits, and the braces are why.** The spawn is `{ _recv_start; } >/dev/null 2>&1 </dev/null &` — the same shape, and the same scar, as `_update_refresh`: a redirected *simple* background command leaks the parent's stdout under dash, so `out=$(claudio run …)` would block until the child exited, which here means for the whole session. Pinned twice, by an elapsed-time assertion and by a static grep for the braced form. Nothing checks that the receiver came up either: Claude Code's export batches over seconds, so it has claude's own startup to bind in.
- **The crash-loop cap, which is the reason a supervisor is safe at all.** A receiver that cannot bind dies instantly and the shim renders several times a second. Three things stop the fork bomb, cheapest first: `recv.err` existing means the fault has already been reported and is not chased again (one `[ -f ]` on the render path, and the file is cleared by a successful bind); **`recv.err` is start faults only, and `recv.warn` is what a receiver that was already up reported** — an undecodable body, a failed write. One file for both meant a live, healthy receiver could write the supervisor's own do-not-spawn flag: one bad payload, then a SIGKILL an hour later, and nothing respawned for that session or any later one. Both are printed by `run` and by `doctor`, and only `recv.err` is a gate; the `mkdir recv.lock` claim is atomic, and the loser walks away rather than waiting because the winner is about to bind the one port there is; and `recv.starts` caps it at `RECV_MAX_STARTS` in `RECV_START_WINDOW`, counted **before** the fork so an attempt that never runs the command still counts. Those two numbers must equal `collector.MAX_STARTS`/`START_WINDOW` and a test compares the two files — a cap that disagrees with itself refuses in one process while the other is still spawning. A lock nobody released is broken after a minute rather than obeyed, and breaking it and claiming it are deliberately *not* one step: the attempt that breaks it stands down.
- **`kill -0` on the render path, `ps` once per session.** A recycled pid answers "alive" wrongly, and nothing portable is both cheap and exact — no `/proc` on macOS, and a start time costs a fork. So `_recv_alive` is one open, two `read`s and a `kill`, all builtins, and the exactness lives in `_recv_is_receiver`, which `claudio run` alone pays for: one `ps` per session, at the exact moment a wrong answer starts costing a session's records. "Cannot tell" answers true there, because respawning over a live receiver can only fail to bind and burn an attempt from the cap. The token in the pidfile is what makes the correction safe: `_recv_clear_pid` removes the entry only while it still carries the token that was read, so a receiver that came up in between does not lose the pidfile it has just written.

**The sessions directory is the receiver's refcount, and claudio cannot be its owner.** `claudio run` writes `<usage_dir>/sessions/$$` **before it asks whether the receiver is alive**, and that order is a fix rather than a preference: the watchdog decides to exit from the sweep at the top of its tick, so a tick landing between "alive: yes" and the registration ended a receiver the launching session had just been told it could export to — measured as `connection refused` two seconds after the check. Registering first removes the tick-sized window; the receiver re-sweeps immediately before it shuts down, which removes the rest. It writes `<usage_dir>/sessions/$$` before `exec claude` — `exec` preserves the pid, so the name really is the claude process — and then claudio is gone and can never come back to tidy up. Removal therefore belongs to whoever is still running: the receiver sweeps the directory on every watchdog tick and unlinks the pids that no longer answer, which is also the half of its idle-exit condition that a timer alone cannot get right. `_recv_session` sweeps too, and that is not a second owner: it is the one case the receiver cannot cover, because if the receiver never starts, nothing else would ever remove an entry and the directory would grow for ever. A recycled session pid reads as live and is kept, which is the safe direction — an entry kept too long costs a late idle exit, one removed too early costs a live session's records.

**Usage recording (stream B) is the half of telemetry OTel cannot give you.** The 5-hour and 7-day plan percentages exist only in the JSON Claude Code pipes to a status line, so the shim is the only place on the machine that can capture them. Three properties carry the design, all `_u_`/`_U_` prefixed:

- **A recorder fault costs a sample, never the render, and never the exit status.** The rendered line is delivered before `_u_record` runs, stderr is discarded, every failure path is `return 0`, and `_u_shim` sets `trap '' XFSZ` (a write past `RLIMIT_FSIZE` raises a signal that kills the shell outright, which no `||` can catch) plus `trap 'exit ${_U_RC:-0}' EXIT` as the backstop for a fatal expansion. The EXIT trap re-exits with the **renderer's** status, so containment cannot turn a working render into a failure or the reverse. The ordering is pinned by a renderer stub that reports whether the sample file existed when it ran — and by a second call proving the probe can say yes, so `sawfile=no` is ordering and not "never recorded".
- **Quantisation is a trigger, never a transformation.** The percentages are compared as canonical integer strings and stored as the raw float byte for byte: the server computes `used_percentage` as `utilization * 100`, which is where `7.000000000000001` comes from, and comparing raw floats fires on every tick. The rounding happens **inside the jq that already parses the payload** (`round | tostring | test("^[0-9]{1,18}$")`), so it costs no process. That is what deletes `printf -v` — for which there is no free POSIX equivalent, `$( )` measured at 682 µs against a 19.6 µs control, i.e. it genuinely forks — and with it `10#`, which in dash is not merely non-portable but fatal: `$((08))` exits the shell. `_u_gt` is `[ "$1" -gt "$2" ]` over digit-guarded strings, and `test` parses base 10, so even a corrupted leading-zero mark is safe. The same jq also reads the clock (`now|floor`), so there is no `date` fork either.
- **A record is written only when the plan has moved.** `_u_win` is a high-water mark per window with forward-only reset acceptance; `resets_at` moving forward is a rollover and is recorded **unconditionally**, whichever way the percentage went. That branch is most of the feature, not an edge case: deleting it drops the replay of 65 real samples from 49 records to 22, and turns a 90%→2% rollover into one record followed by permanent silence.

Three guards exist to stop a window freezing **for good**, because none of them has a self-healing path: the ≤18-digit rejection on a quantised value (`used_percentage: 1e30` stored as a mark nothing can beat), the epoch floor of 1000000000 (the real data contains `resets_at: 1`, which reads as an ancient window and makes every later tick a rollover) and the ceiling of now+30 days (one millisecond epoch is ~55 000 years out, and `_u_win` then reads every honest epoch as a stale snapshot). **Marks read back out of the state file get exactly the validation an incoming one gets** — a shared `usage_dir`, one hand edit, or a machine with a different clock would otherwise stick permanently. Two of these are belt and braces whose mutation no test catches, and the comments say so rather than implying coverage: `test` on dash and bash *saturates* an out-of-range integer rather than wrapping, so the `${#1} -le 11` length check is unreachable here — it is kept because POSIX leaves that behaviour undefined and the bash original used `$(( ))`, which does wrap.

Preserved verbatim from the bash original because each was learned the hard way: the `-` sentinel in the state file (tab is IFS *whitespace*, so a run of tabs collapses and an empty field disappears, silently shifting every later mark); temp+rename with `$$` for the state write; the refusal to use `$HOME/.claude` as `usage_dir` however configured; and the **1023-byte** line cap. That cap is not PIPE_BUF — this is a regular file opened `O_APPEND`, where one `write(2)` is atomic at any size — it is the shell's stdio flush unit, `BUFSIZ`, 1024 on Darwin. Measured: 16 concurrent writers tear never at 1023 bytes and immediately at 1024, identically under dash and bash. Anyone "fixing" it to 512 to match PIPE_BUF halves the usable record for nothing.

Two deliberate departures from the source. `agent` read `.agent?.name?` against a payload carrying `agent_type` at top level, so it was null in all 65 real records — ported as the fix. And the state file stays at **version 2 with `prec` fixed at 0** rather than bumping to 3: `prec=0` already meant integer marks, so a file the source wrote is still comparable and nobody is forced through a spurious `first`. (jq's `round` is half-away-from-zero and C's `printf %.0f` is half-to-even, so the two can differ by 1 at an exact `.5`; `fixtures/derive-expected.py` says so and matches jq.) `usage_precision` and `usage_heartbeat` are dropped — they are not in the agreed key list — but the `prec` slot stays so a future key needs no second version bump.

The `_u_peel` guard is the one thing most likely to be "simplified" back into a bug: `${1#*"$NL"}` on a string with **no** newline returns the string unchanged, and `$( )` has already stripped every trailing newline, so a naive peel re-reads the last field for ever — exactly where `prompt_id` and `agent` are empty. The 19th field is a constant sentinel, so a drifted field list drops the record instead of assembling one out of shifted variables.

**The step between the two streams is the one that ran never.** `cu/ingest.py` is `claudio usage`'s ingest, **moved** there rather than copied — the same move `tail.py` got, for the same reason: a second reader needed it. That reader is the receiver's watchdog. Until it existed, `do_ingest` was reached from exactly two places, both in `claudio usage main()`, so on a fully configured `logging=remote` machine the receiver wrote `raw/`, the shipper read `ledger.jsonl`, and nothing turned one into the other: the ledger never existed, `_ship_stream` answered "no such file yet; nothing to say", `run_pass` recorded no failure and cleared `ship.err`. Reproduced with real processes — 7 real payloads captured durably, the real door, several ticks, **zero** stream-A batches accepted, both `ship.err` and `ship.warn` absent, while stream B shipped perfectly. A machine delivering plan percentages and no request rows is indistinguishable on the server from a machine that made no requests, which is the exact failure `logging=remote` exists to close. The tick takes the same `flock` a manual ingest takes and treats a refusal as a skipped tick (`ingest_lock(cfg, on_busy=…)`), so the automatic pass can never double a ledger. Two consequences worth keeping: `_ingest_then_ship` is one function because the order is load-bearing (the shipper reads what ingest writes), and the receiver is the only process that knows both that records arrived and that the ledger is absent, so that combination is *its* warning to write, not the shipper's — which is why it is a `recv.warn` and not a `ship.err`.

**Rotation now asks the ingest offset before it unlinks.** `Capture._rotate` had no interlock at all, and while nothing ingested automatically the deletion was not an edge case — it was where the records went: 6000 real payloads at `raw_max_megabytes=1`/`raw_max_backups=2`, then one ingest, 1900 rows and 4100 records gone, with `doctor` printing `6000 accepted -> 6000 written` directly above `ledger rows: 1900` and exiting 0. A backup whose stored offset is short of its size — or that has no entry at all — is kept past the cap and named in `recv.warn`; cannot-tell answers *keep*, for `_recv_is_receiver`'s reason. A raw directory that grows is visible in a byte count and is emptied by ingesting; a deleted record is neither. `doctor` compares the two numbers itself now, because they sat three lines apart in one function with nothing between them.

**`usage/` is the reader for what the shim records, and it is a different language on purpose.** claudio writes `samples.jsonl`; `usage/claudio-usage` ingests that plus Claude Code's OTLP export into a ledger and prints breakdowns. It is Python with its own suite (`python3 usage/tests/test_all.py`), and the no-bash-isms rule does not reach into it — the recorder must run in a status line several times a second, the reader is invoked by hand. The seam between them is one path: `usage_dir` (default `~/.claudio-usage`), which both sides default to and the readme states as a contract.

**The seam is resolved once, on the side that has the layering, and it was resolved on neither.** `usage_dir` layers global → profile → project, and the shim, `_run_receiver` and the receiver spawn all honour it — while the Python half read `CLAUDIO_USAGE_DIR` from the environment and otherwise defaulted, and `cmd_usage_cmd` exported nothing. So `usage_dir=/data/usage` recorded into `/data/usage` and `claudio usage show` read `~/.claudio-usage` and printed `No requests recorded yet.` over a full ledger, with `doctor` printing two zeroes beside it: the cardinal sin, on the one key whose whole job is to say where the data is. `cmd_usage_cmd` now resolves it with the same helpers `_statusline_recording` uses and exports the result, rather than a second resolver in Python that would have to agree about the layering for ever; an explicit `CLAUDIO_USAGE_DIR` is the narrowest layer on both sides and is not re-decided; and a `usage_dir` inside `~/.claude` is **named on stderr** rather than passed on, because claudio refuses to write there and a reader aimed at it reports an empty machine and is believed.

**`CLAUDIO_SELF` is the same fault pointed the other way.** `claudio usage doctor` asks claudio two questions — `claudio env` for the stream-A export, `claudio statusline` for whether recording is on — and it asked them of a **bare name**. Resolution only runs downhill (claudio finds its Python through `_tool_path`'s three layouts and handed nothing back), so a checkout's `./claudio usage doctor` interrogated `/usr/local/bin/claudio`: a different build reading a different config. Reproduced as `Recording plan usage: on (logging=local)` from one and `recording is OFF — claudio reports nothing configured at all; add logging=local to <conf>` from the other, naming the file that already held the line. Unhelpful became confidently wrong, from the one command whose job is to say what is wrong. The resolved path is exported and `doctor` prints **which claudio it asked** beside `data root:`, because an answer attributable to no particular binary is one nobody can check; the fallback is still the bare name, for `usage/claudio-usage` run by hand. Pinned with two stubs that contradict each other, since one stub cannot tell "asked the right one" from "there was only one to ask".

**The client got the three empty answers the server has had all along.** `--since` was applied before the emptiness test, so a filter that eliminated every row printed "No requests recorded yet." over a full ledger; it now names the clause, the value **as typed** (the parsed float is not a bound anybody wrote) and the count it removed, and says outright that the ledger is not empty. `--by <key>` that no row carries — as a column *or* as a `--tag` — is refused with the list of keys that are there, and the code comment defending the old behaviour as "visible and self-explanatory" is **withdrawn rather than left to argue with this file**: `--by profile`, the default and a real column, renders one `(none)` bucket over the same fixture, so a typo and a real column full of blanks were byte-identical output. An arbitrary tag key stays legal; the axis a user invented is the axis they meant.

**And `~/.claude-usage` → `~/.claudio-usage` had no migration, no hint and no note.** `migrate` covers `~/.claude` → `~/.claudio` and nothing else, so a machine recording before the rename got a fresh empty directory and two zeroes — indistinguishable from one that never recorded. Nothing is moved automatically, because it is somebody's data and a diagnostic command is the wrong shape to be relocating directories with; `doctor` names it, with both remedies, **only** when the new directory is empty and the old one is not, since either condition alone makes the line noise.

**Its one hard invariant is that a drop is never silent, and the four ways it was:** an ingest racing another ingest (`collect stop` ingests by itself, so this is one keystroke away — reproduced as 16 ledger rows for 8 requests with `doctor` reporting health); a record skipped because Claude Code renamed `event.name`, with the byte offset advancing past it so `--from-zero` cannot recover it either; a complete payload appended to the fragment of an interrupted write, so `json.loads` failed on the pair and the good half died with the bad; and two different requests hashing to one `request_id`, which is byte-indistinguishable from an idempotent re-read because *every* tie-breaking field is deliberately outside the hash. The fixes are, in order: an `flock` that refuses rather than waits, a skipped-count that **names** the event it saw, a retry from the last `{"resourceLogs"` in the line, and a fingerprint comparison that reports the collision. Two rules bind all four. **The hash is never widened** — that re-identifies every row on disk and doubles the ledger on the next ingest, so a collision is reported, never repaired; for the same reason absent token counts are stored as `null` but hashed as `0`. And **exclusion and read-side dedupe are both required**: a lock cannot undo a doubling that already happened, and deduping on read cannot stop one happening. `doctor` is the other half of the promise: every `WARN` it prints now sets a non-zero exit, because it used to print `WARN ledger rows: 0` and exit 0.

**`doctor`'s recording verdict has three answers and had two, and the missing one was the state every fresh install is in.** `_claudio_recording` asked `claudio statusline` and read its `Recording plan usage:` line. With nothing configured at all that line is never printed — `statusline` prints "No status line configured", exits 1, and is right to — so the function returned a bare `None`, which `doctor` rendered as `WARN recording: claudio not on PATH`. A confident diagnosis of a problem the user does not have, printed by the one command whose whole job is to say what is wrong, at the one moment they are most likely to run it: it sends them to fix a `$PATH` that is already correct while the remedy is one config line. The reason now travels with the state, the "nothing configured" case is decided from claudio's **own words** rather than inferred from the absence of a line — an inference across two programs is how the wrong reason got here — and "claudio cannot be run at all" stays reachable, because deleting a true diagnosis along with a false one is the other way to lose. There is a fourth answer under the third, found by running the suite and reading what it printed: a claudio that **was** found and exited non-zero — a broken shebang, an install too old to have the verb — used to be reported as "not on PATH" and would have become "ran but reported no recording state", which is the same invented cause one step milder because it asserts the process succeeded. It quotes the exit status and the program's own stderr instead. The four are stubbed as real `claudio` scripts on `$PATH` and each verdict is pinned, because a stub is the only way to hold all four still on one machine.

**Two of those four fixes were pinned by tests that could not see them fail.** The lock's refusal test held an *exclusive* lock and asserted the ingest refused — but a `LOCK_SH` request is refused by a held `LOCK_EX` too, so `LOCK_EX → LOCK_SH` in `ingest_lock` left the suite green while two shared holders coexisted and both ingests appended everything. Only a **shared** holder separates the two, so that is what the test takes now; and the *scope* of the lock — the docstring's central claim, that it spans read-ids/read/append/save-offsets — is asked from inside a patched `ledger.append`, because `with ingest_lock(cfg): pass` followed by an unlocked ingest also used to survive. The same trap — an assertion satisfied by prose *about* the thing rather than the thing — killed the counters test one directory over, which searched the collector config for `host:\s*0\.0\.0\.0` and matched the **comment** explaining why that setting was load-bearing. That config is gone with Docker, and the successor test is behavioural for the same reason: the durability assertion reads the capture file from the *client*, with no sleep between the response and the read, and is paired with a negative probe proving the file did not exist beforehand — so it cannot pass by having been written at some other time.

**The counters moved from a Prometheus scrape to the receiver itself, and they answer one more question than they used to.** otelcol's `:8888` told you accepted-vs-exported; what it could not tell you was what *never arrived*, because `raw/api_request.jsonl` was the collector's own **output** — a field deleted by `keep_keys` was invisible in the only file anyone read, which is how `prompt.id`, every user `--tag` and `agent.name` were each lost in silence. `recv/otlp-recv` counts at the door: `events` names every distinct `event.name` seen and `unknown_attributes` names every attribute key that arrived with no ledger column. So the two failures that used to wear each other's face are separated in print — `0 accepted` with an empty `events` is nothing arriving, while `events: user_prompt 4` with no `api_request` is drift, and `reconcile_text` says so outright rather than leaving it to be inferred from a zero. The comparison set is `otlp.STORED_ATTRS`, and a test **derives** the reader's own `a.get("…")` calls out of `cu/otlp.py` and compares the two sets, because a hand-maintained copy would recreate the blind spot one level up: a permanent false alarm trains people to ignore the counter exactly as a missing one does. Counters are also snapshotted to `recv-counters.json` on every watchdog tick — the process exits after an idle half hour, so counters that died with it would report "nothing arrived" for every session already finished.

**The receiver is spawned on demand and exits by itself, and the three arguments for a service are all settled.** Its flush argument was measured false (see the bind-mount trap below). Its coverage argument was near-empty: `_build_env` writes the OTLP variables only into the environment of the `exec`ed claude, so stream A does not exist outside claudio-launched sessions and an always-on listener is attached to an unplugged wire. And `launchctl`/`systemctl` cannot be stubbed in a hermetic suite. Not `otelcol-contrib` either: idle self-exit is in the design and it cannot do that without a second watcher process — the daemon returning by the side door — and it is 93-107MB with no formula. **Idle exit needs both of its conditions**, no records for `idle_minutes` *and* no live pid under `sessions/`: a timer alone orphans a user who reads for forty minutes with claude still open, and a session check alone never exits once a file is stranded by a crash, which is a daemon nobody chose to install. **A crash loop refuses itself**, because a receiver that cannot bind dies instantly and a supervisor checking `kill -0` on every render would fork-bomb; starts that never reached a bind are counted in a window, and past the cap it writes `recv.err` and exits without binding. The supervisor will carry a cheaper cap of its own — this is the backstop that holds when the supervisor is wrong, and the half that can leave a note saying why nothing is recording. **The pidfile carries a token as well as a pid**: `kill -0` answers "alive" for a recycled pid, nothing portable is both cheap and exact, so the pidfile is removed only by the receiver whose token it carries — otherwise a receiver shutting down while its replacement is binding deletes the new one's pidfile, the supervisor respawns over a live process, and the user reads a `recv.err` about a fault that never happened. Eleven contract paths (`recv.pid`, `recv.lock`, `recv.err`, `recv.warn`, `recv.starts`, `recv-counters.json`, `sessions/<pid>`, `raw/api_request.jsonl`, and the shipper's `ship.err`, `ship.warn`, `machine-id`) are declared once in `cu/config.py`, because the other half of the contract is POSIX sh and cannot import them, and each is line-oriented so the shim reads it with builtins and no fork.

**`kept`, not `wrote`.** The drift line's middle figure is records that *parsed*, and calling it `wrote` put a false claim directly above the true one — "wrote 1" over "ingested 0 new requests" — on every `--from-zero`, on the rescan after a rotation and on any overlapping re-read, i.e. exactly the recovery paths someone runs when they already suspect data is missing. Only the `ingested N new requests` line claims a write, and a test now ingests one drifted file twice so the two lines are pinned against each other; the first pass cannot catch it, because there the figures agree by accident.

**A refuted claim is scanned for across every doc under `usage/`, not in the module that was corrected.** Three files had the buffering claim rewritten and a fourth, `recv/README.md`, kept asserting it verbatim beside the very `collect start`/`collect stop` commands it documents — the repo saying both things at once, with the measured-false copy in the most believable place. The scan therefore walks the directory, and three details are the whole of its strength: the text is **flattened** first (`usage/README.md` carries "does not\n> flush on idle", the claim spelled exactly and invisible to a literal `in`); **every** occurrence is checked rather than the first, because a file that refutes the claim in one paragraph and asserts it in the next is the same defect at file scale; and the refutation window is **200 characters**, slack over the 114 of the furthest real one, because at 500 an uncorrected paragraph passes by standing next to a corrected one. Both mutations were run and both now fail.

**One decision, one implementation: the receiver filters nothing.** The Docker collector dropped every event that was not `api_request` and ran the survivors through a `keep_keys` allow-list; `cu/otlp.py` then did both jobs again one layer in, because it stores exactly the columns the ledger has and skips every other `event.name`, counting and naming what it skipped. That is one decision implemented twice, and it is how three fields were dropped in silence — each half looked right beside the other, and the file everyone read was the output of both. So `raw/api_request.jsonl` is now the bytes as they arrived, `cu/otlp.py` is the only place that decides what a row is, and what it does not keep is countable at the door. Two costs, stated rather than buried: the file holds `user_prompt` and `assistant_response` too and therefore grows faster (rotation is now the receiver's, at lumberjack's old 32MB/16 figures), and the log record body is stored as it arrives — Claude Code leaves it empty unless `OTEL_LOG_USER_PROMPTS=1`, which is the user's own opt-in, and a silent redaction here would be the second invisible policy this whole paragraph argues against.

**Two user-visible strings that a release pins for ever.** The receiver overrode only `log_message`, so every reply carried the stdlib default `Server: BaseHTTP/0.6 Python/3.14.6` — a program that does not exist in this project, and the machine's exact Python patch version, published from a listening socket. The sibling door in `server/` had been fixed in the same sweep and this half had not, which is the wrong half to leave: the door runs on one receiving host, the receiver runs on every user's machine, and `recv/README.md` tells people to curl its `/healthz`. It is `claudio-recv/1` now, with the same `version_string()` override the door needs (an empty `sys_version` otherwise leaves a trailing space) and the same **exact** comparison in the test, since the defect *is* the suffix. And `synth-otlp --help` printed `**Not authoritative.**` with the asterisks, because its description came from `__doc__.splitlines()[0]`; the docstring stays Markdown for whoever opens the file and the description is a plain constant, exactly as `claudio usage` already does it. That file is installed and documented by path, so it is a user-visible string and not an internal one.

**The two Python verbs answer a bare invocation the same way, and a guard reads what it extracts.** `claudio usage` returned 1 and `claudio recv` returned 2 — two verbs of one tool, one situation, two statuses, against claudio's own convention of 1 everywhere (`mcp`, `default`, `show`, `Unknown command:`). And the receiver's log-prefix guard extracted every stderr line into `lines`, asserted `len(lines) >= 5`, and then **never used it**: its two real assertions were that `[otlp-recv]` appears nowhere and `[claudio recv]` appears somewhere, both of which an unprefixed line satisfies vacuously — and there was one, `cmd_tail`'s sole diagnostic, printed by a first-run command on a machine with no capture. The docstring claimed every line; the code asserted two. It asserts the extraction now, and every option of every parser is required to carry a `help=` — which immediately found two more with none.

**Its fixtures are real captured payloads with the identities replaced, and re-capturing them is the trap.** Synthetic addresses, account labels and UUIDs are mapped *consistently* — the same UUID everywhere, or the joins under test stop joining — while structure, field names and token counts are left byte-exact. That combination is the point: a synthetic generator was written once to match the collector's own filters, so the two agreed with each other while both disagreed with reality, and it hid a wrong event name that dropped every record and an allow-list that deleted every user tag. Both suites were green. So refresh the fixtures from a real machine when the payload shape changes — and scrub them in the same commit. Anyone who captures and commits without scrubbing publishes their own address, account UUIDs and session IDs into a public repo, which is exactly what nearly happened here.

**`server/` is the reconciler, and it is a pure function over records.** `srv/` imports nothing that touches a file, a socket or a clock — a static test walks the package and asserts it — because `now` being an argument is what keeps the storage decision open and what makes a week-late shipment retroactively correct a window that closed days ago. **`srv/serve.py` is the one exception and it is named in that test rather than hidden from it**: the impure set is asserted to be exactly `{serve.py}`, so a second module that opens a file has to be admitted in the suite before it can exist, and a second test asserts `srv/__init__.py` never imports it — otherwise a pure consumer writing `import srv` would pull `http.server` and a clock in through the package's front door and the purity rule would be a statement about files rather than about what loads. Its justification is the one the design note gives: local attribution was built, worked and was deleted, because the plan percentage belongs to the *account* and one machine cannot see double counting, invisible surfaces (browser, phone, an un-instrumented laptop) or the missing baseline after a gap. Its suites are `python3 server/tests/test_all.py` and `python3 server/tests/mutate.py`; `test_reconcile_adversarial.py` is a deliberately **red** file holding findings that are not fixed yet, and a repaired finding **moves out of it** into `test_all.py` with a mutation beside it — a fix pinned in a permanently-red suite is pinned by nothing, since nobody reads a red file for a new red line and `mutate.py` refuses to run against a red tree.

Five invariants there were each a wrong number before they were a rule:

- **A rate is fitted per `(account, kind)`, never per account.** A percentage point of the 5-hour limit and one of the weekly limit are fractions of different plans with different denominators — the same rule that forbids summing across accounts, one level down. It was not a tie: a 7-day window's weight is a *superset* of every 5-hour window's inside it and its movement is `peak - trough` rather than `peak - 0`, so its ratio is structurally the smallest and `min` chose it the moment one weekly window had closed, permanently thereafter. Measured on 16 fully instrumented requests: the 7-day window explained itself exactly while the same rows read through the 5-hour windows reported residual fractions up to 87% — identical evidence, two reports, 0% and 87%. A **bare number** handed in as `rate` now raises rather than being spread over both plans.
- **Two `resets_at` of one kind cannot be closer than the window length**, because a window opens no earlier than its predecessor's close and then runs a full length. Three independent guards, and the tie branch is what keeps the middle one reachable: the closer bucket is **refused by name** (chosen by sample count — one stray record against eighteen is the stray, which is evidence rather than a coin flip); on a tie both are kept and `start` is **clamped** to the previous `resets_at`, so membership is a partition *by construction* and not as a consequence of the refusal rule firing; and `fit_rate` refuses to let a clamped sliver pin a rate. One stray record 100 s off counted 19 requests as 38, pinned the rate 19× too low, and moved the real window's residual from 0% to 95% — and `gaps()` said nothing, because it only tests `b.start > a.end`.
- **Bound quality is an eligibility criterion, and it is a preference rather than a floor.** `movement_lo` is `max` over the samples that were *seen*, so a laptop that sleeps through the end of a window reports a peak far below the terminal value and `min` selects precisely it. `MAX_GAP_FRACTION = 0.25` is read off the capture — the five real gaps are 0.2%, 2.2%, 13.7%, 27.7% and 95% of the window, and the only wide separation is between 13.7% and 27.7%. It is a preference because **every** 5-hour window in the joint capture has a 78% gap: a hard floor would refuse to fit a rate on the only real multi-account fixture there is. So a well-observed window outranks a blind one, and when every candidate is blind the tightest still pins it and `basis` says outright that it did. The pinning window's gap, movement, weight and coverage then travel as a **note on every attributed row**, because `rate_is_from_this_window=False` on a row whose own evidence is perfect is not a caveat anyone reads as one.
- **Last EMITTED wins, not last arrived.** `emitted_at` was declared in `ATTEST_FIELDS` and read by no line of code, and attestations were last-write-wins — but batches arrive out of order routinely, a machine catching up ships old ranges after new ones. Two attestations from one host for one window, one covering all of it and one covering none: stale last gave coverage 0.0 and the refusal "no machine was observed listening during this window", a claim that machine contradicted in a record the server was holding. Coverage is the guard on the residual, so this is the one number the design protects. Equal `emitted_at` is not a tie to break — the spans are merged, deduped so a re-ingest stays a no-op — and an arrival older than what is held is counted and refused *by name*, apart from an idempotent re-emission.
- **A record is refused by name or it is placed; nothing is emptied in between.** `_clip` dropped an unreadable `up_spans` element with a bare `continue` and `wire.check` never looked at `up_spans` at all, so a malformed attestation was accepted, emptied, and reported as `dark` — which this module's own docstring calls "a positive statement" that the machine was not listening. `wire.check` refuses it (`attestation-unreadable-spans`), and `_clip` **counts** what it could not read anyway, because `reconcile` also takes attestations directly; `settled_zero` cannot fire while any span was unreadable. Same shape one file over: a ledger row with an unusable `ts` was in no window's request set and in no `unclaimed` list either, so its weight silently landed in the residual — it is now a third bucket, `undatable`, named in the report. And `Report.refusals` is `all_refusals`, not `[]`: the variable was accumulated and thrown away, so the anti-silence surface reported a silence.

**`srv/query.py` is the reader, and it is pure for the same reason the rest is.** It is handed rows and returns answers — filters over any stream-A column with time ranges and free text, id lookups, breakdowns by any column or user tag, keyset pages, and a re-shaping of the reconciled windows — so every behaviour is testable without a socket. Four decisions carry it. **Three empty answers are three different values**: `no-data` (nothing scanned), `filtered-to-nothing` (scanned and every row eliminated, with the *clause* that did it named out of a per-clause elimination count) and `Unanswerable` (the question is not answerable at all, with a reason and a remedy). `claudio usage show --by nonsense` used to group every row under `(none)` and print a tidy table, which is the third answer wearing the second one's face — and the client's own comment defended that as "visible and self-explanatory", a defence that does not survive `--by profile`, the *default* and a perfectly real column, rendering one `(none)` bucket over the same fixture: a typo and a real column with absent values were byte-identical output. The client refuses it now, on the one condition that separates them — **no row carries the key at all**, as a column or as a `--tag` — and names what is available; an arbitrary tag key stays legal, because the axis a user invented is the axis they meant. **Every aggregate carries a `CoverageStatement`**, and over real data today it says `fraction: None, basis: "no-attestation"` — nothing emits an attestation, so "nobody said" is the truth and `0.0` would be the claim "nobody was listening"; beside it sits placement, which is always computable, so a breakdown states how many of its rows fall in a closed window, an open one, no window at all, or carry no usable timestamp. **There is no cross-account total in the file, not even for tokens** — a rule with an exception in it gets applied by whoever remembers only the exception — and grouping *across* accounts by `account` or `email` is refused by its own name, because `--tag account=` overwrites the first and the second survives an orphaned login, so two accounts sharing a label would silently become one bucket. **Pagination is keyset over `(ts, request_id)`**, both immutable per row, because this store is designed to accept a week-late shipment: under an offset a row appended into the middle of a page served yesterday shifts every later row by one and skips a real request in silence. What keyset cannot show — a row arriving *behind* the cursor — is printed on every page with the remedy, and a cursor from another query or another direction is refused rather than applied.

**The index is measured, and it is now a measured storage layer with a measured projection behind it.** A linear scan was measured rather than assumed, and re-measured against the row that is actually on the server: **7.706 s/GiB** over a **789.3**-byte mean row, not 6.675 over 737 — 737 is the row the *client* writes and 789.3 is the row in the store, which carries the `account_uuid` the shipper stamps on, so five years is 62 M rows and **48.9 GB / 45.6 GiB** and the whole-file scan is **351 s**, not 284. The old pair had been quoted in three places and was measuring the wrong end of the wire; both are corrected together and the correction is stated rather than slipped in, because a re-baselined number with no note is indistinguishable from one that was always right. Stream B is deliberately left unindexed — the whole five-year corpus is 339k rows / 202 MiB — because the reflex is to index both.

**DuckDB is the storage layer, it is the first non-stdlib dependency in the project, and it is permitted in one place.** It reads `accounts/<uuid>/*.jsonl` **in place**, which is the whole argument: the JSONL stays the record of truth, nothing is migrated, there is nothing to rebuild after a crash, and real SQL joins across the two streams become possible — which is what ad-hoc correlation needs and is the one thing the hand-rolled engine cannot do at all. `srv/duck.py` is **pure** (it builds SQL strings and maps values, opening nothing) and `srv/store.py` is the connection, so the purity test's exception set moved from `{serve.py}` to `{serve.py, store.py}` — asserted in the suite, which is what forced admitting it before it could exist. `claudio usage` and everything under `usage/` still read the same JSONL with the standard library, offline, with no server and no daemon, and **a test walks the whole of `usage/` and asserts nothing there imports duckdb**; claudio gains nothing at all. Without it `store.require()` raises `DuckDBMissing` naming the install command, never an empty result — "0 requests" is a perfectly plausible answer for an account that has not shipped yet, so a layer degrading into one is indistinguishable from a working one over a quiet account.

**The container holds the pin, and it stops at `server/`.** DuckDB existed on the developer machine only inside a `/tmp` venv, which does not survive a reboot, and a machine without it runs **1516 passed, 0 failed, 45 skipped** against **2448, 0, 0** with it — 932 assertions, 38% of the suite, not run. (Re-measured at every pass; it was 1147/2065 when this was written, 1154/2072 mid-packaging and 1164/2082 at packaging, and the gap held at 918 across all three. It was **919** at the image work, with the skipped test functions up from 44 to 45 — one further test now needs the engine — and is **932** after the image findings were repaired, the skipped count unchanged at 45 — the gap held while both totals moved, which is the shape a healthy addition has. The gap, not either total, is the figure the argument rests on, so a change in it is the thing to chase rather than to overwrite.) They are announced rather than silent, so it is not the cardinal sin; but `1516 passed, 0 failed` is the sentence a reader acts on and 45 `SKIP` lines scroll off the top of a terminal while a summary does not. So a skipping run prints a banner **after** the summary, naming the interpreter that could not import the engine and saying outright that the run is not evidence about it, **and exits 1** — that default is a correction: it used to be exit 0 with the banner, so `make check`, which runs this file and is the documented release gate, reported success over 918 assertions that never ran. `--allow-skips` is the one-word escape hatch and says out loud what it accepted; `--require-duckdb`, which `compose.yml`'s `suite` service passes, is now redundant and still accepted, because an environment built specifically to supply the engine saying so is documentation rather than ceremony. The banner is prefixed `!!` rather than starting a line with `SKIP`, since `mutate.py` collects baseline skips with `startswith("SKIP")` and a banner that looked like one would inflate the count it refuses on. `server/Dockerfile` carries **no source at all** — the repo is bind-mounted, read-only for the two test services, so nobody rebuilds an image to run a test and no snapshot of the source can go stale inside it — and the build **asserts what it installed**, because `pip install duckdb==X` can succeed with a different version importable and an image whose engine disagrees with its own pin is a reproducible home for the wrong thing. The version is derived from `duck.py`'s own "measured on 1.5.5" comments rather than hardcoded in the test, for the reason every other doc guard here derives its list: a hardcoded copy is a fourth place to forget. Floating the version would leave those five refusals' sentences in place while deleting the evidence for them.

The boundary is the point, and it is asserted three ways rather than intended: a static walk of `usage/` for `import duckdb` by any spelling, a behavioural run of the real `claudio usage show` with the name **blocked at the import system**, and a directory listing requiring that no container file or dependency manifest exists under `usage/` or at the repository root, that `claudio` never names `duckdb`, and — positively, so the test fails if the container is deleted as well as if it spreads — that the Dockerfile and compose file are in `server/`. A boundary test that only forbids passes trivially once the thing it bounds is gone, and then says nothing when it comes back somewhere else. Two container-guard drafts were mutated into survival before this landed and both were the same shape: `--require-duckdb` is named in the comment that explains it, so a whole-file `in` passed with the flag deleted from the command, and `--port "8787"` matched a ports-list grep scoped to the whole service block — co-occurrence asserted instead of configuration, the `account.<name>.ship_*` doc-guard defect twice over. Every guard is now scoped to one service's block, or to one list inside it. **The image has since been built and all four services run** — Docker 29.6.2, Darwin arm64 — so `server/README.md`'s table is now a record of what was *observed* rather than an UNVERIFIED one: the build resolves to Python 3.12.14 with duckdb 1.5.5 importable and its own version assertion satisfied, `run --rm suite` reports **2448 passed, 0 failed, 0 skipped** and exits 0 under `--require-duckdb` (the identical count to a host venv, so the container is not a different tree — re-run at every pass since and still identical: 2065, then 2072, then 2082, then 2298, then 2448, both sides each time), the `:ro` mount refuses a `touch` with `Read-only file system`, and the door answers `/healthz` and `/api/v1/capabilities` through the published mapping while printing both trust warnings verbatim. The static checks that preceded it are kept in the same table rather than replaced, because they are what a developer with no daemon can still run. Worth recording as a shape rather than a fact: every one of those static conclusions turned out to be right, and being right is still not the same claim as having been run. `--host 0.0.0.0` in the `door` service is the container's own namespace and not a relaxation: the publish mapping is pinned to `127.0.0.1:8787:8787`, `8787:8787` is exactly how this would face the internet, and the process's two trust warnings are printed on every start and remain true.

**Measured, not assumed, and the numbers pick the design.** At 45.6 GiB every query is **~8.1 s** — filtered search 8.06, terms 8.32, histogram 8.16, `request_id` lookup 8.34 — which is 43× **faster** than the 351 s Python scan it replaces and still not interactive, and *does not improve with a narrower question*, because reading the JSON is the work and there is no index to skip it with. In-place JSONL is interactive below about **1.1 GiB** and not above it. A **Parquet projection is 115× faster (0.070–0.202 s), 22× smaller (2.03 GiB) and builds in 36 s**, which is exactly the derived-deletable-projection shape the storage pass specified and plugs into the seam `narrowing()` already stated; a persisted DuckDB database is the worse of the two — same speed, twice the bytes, and it is a *database file*, the one thing the record of truth must not become. **Nothing has been built to maintain a projection**, deliberately: the crossover is documented and no real store is near it, and building maintenance for a problem nobody has is how the record of truth quietly becomes a database. The join is the honest counter-example and is stated twice: a range `LEFT JOIN` is **185 s over JSONL and 184 s over Parquet** — the projection buys it *nothing*, because a non-equi join cannot use row-group statistics and the cost is the comparison, not the read. "Correlation is now possible" must never be read as "correlation is now fast".

**Five things DuckDB does silently, each of which is a refusal in `duck.py`.** Every one of them produces a plausible answer, which is why they are in the source and in `server/README.md` rather than in a commit message.
- **Inference DROPS a column.** 30 000 real rows with `cache_read_tokens` absent from the first 25 000 — inside the default `sample_size` — and `read_json_auto` returns **29 columns instead of 30**: `SELECT *` a column narrower, `GROUP BY model` answering cheerfully, and only a query naming the column by hand erroring. Cache reads were ~89% of this user's tokens, and a front end that derives its column list from the relation — which is what "hold no list" demands — renders it simply gone. So the schema is **pinned** from `wire.LEDGER_FIELDS`, there is no code path that omits `columns=`, and a test asserts the key set against `wire`.
- **A pinned list is blind to a new column**, so the new ones are counted: `store.unknown_keys()` names every key in the files the pinned list does not carry. That is `cu/otlp.py`'s allow-list one layer down, and that allow-list is how `prompt.id`, every user `--tag` and `agent.name` were each lost in silence.
- **`ignore_errors=true` does not skip a malformed line — it emits a row of NULLs.** 1000 good records plus one torn fragment gives `count(*) = 1001`. A torn final line is the ordinary state of a live store (`Store._append` guards against gluing a fragment onto a good record for exactly that reason), and *without* `ignore_errors` the whole query dies instead, so one torn byte range becomes a store that answers nothing. `request_id` is a content hash present in every real row, so `request_id IS NULL` is exactly the malformed set: excluded from every count and every page, and **reported** as a store problem rather than quietly subtracted.
- **A pinned `BIGINT` COERCES rather than refusing:** `1.5` arrives as `2`, `"7"` as `7`, `true` as `1`, no warning on any of the three. The token columns, `duration_ms`, `ts_ns` and `schema` are integers in all 8 real rows so BIGINT is what they are, and the coercion is named rather than discovered. The seven **never-observed** columns are pinned `JSON` instead, which is the whole reason they are a separate list: nothing has ever stated what arrives in `event_sequence`, and typing it BIGINT because the name ends in "sequence" is the assumption-written-as-a-value this project keeps apologising for. `JSON` keeps the value *and* its type, so `5` and `"5"` are still different when somebody finally looks — and that asymmetry is load-bearing in the text search, where `json_extract_string` over a JSON `5` returns the string `'5'` and the `json_type(...) = 'VARCHAR'` guard is the only thing stopping the two engines disagreeing the first time anybody searches for a digit.

- **Every value binds, and the one thing that does not is an identifier.** An earlier draft quoted its values into the SQL, justified by the claim that binding "is not available for a table function's path argument" — measured on 1.5.5, that is **false**: the path, a list of paths, the pinned `columns=` map (types preserved exactly), a value inside `FILTER (WHERE …)`, a row comparison, `LIKE … ESCAPE`, a JSON path and `LIMIT` all bind. That is not tidiness. Interpolation carried a live defect with no injection in it: `repr(float("-inf"))` is `-inf`, which DuckDB reads as a **column name**, so `since=-inf` — an ordinary "no lower bound" that `serve._num_param` accepts today — matched all 8 real rows through `query.py` and raised `Binder Error: Referenced column "inf" not found` through this one. What does *not* bind is an identifier, and that measurement is the opposite of reassuring: `SELECT $c` with `c="model"` returns the constant **string** `'model'` once per row, no error anywhere — so a column name has exactly one possible defence, the whitelist `query.compile_query` applies before `duck.py` is reached. Parameters are **named**, not positional, because `accounting_sql` embeds the whole predicate three times and a positional repeat in the wrong order is a wrong answer rather than an error; DuckDB refuses a parameter dict carrying a name the statement does not use, which is what makes the pairing self-checking and why a `Params` is never shared between two statements.

One more, from the client rather than the engine: `to_timestamp()` returns `TIMESTAMPTZ` and converting one to Python **requires `pytz`** — a second non-stdlib dependency acquired by writing an ordinary date histogram. Epoch arithmetic avoids it and avoids asserting a time zone the data does not carry.

**The Python predicate is now the ORACLE, and that is what makes the storage layer safe.** `Narrowing`'s one-directional contract — a storage layer may return a superset and must never return a subset — is enforced rather than described: a differential test runs every query shape through `query.select` and through `store.select` over the same real rows and requires the identical answer, row for row, count for count, clause label for clause label. It has already earned its place, catching four divergences on its first run, one of which (a tag value returned as the JSON text `'"4"'` rather than the string `4`) no reader would ever have suspected. **`scanned` legitimately differs and is asserted rather than excused:** the per-account file layout *is* the narrowing, so an account-scoped query opens one file and scans fewer rows than the oracle, and its account clause therefore eliminates none of them — which also means a `filtered-to-nothing` names the clause that really did it rather than blaming the account. A count that quietly meant something different in one engine is how two figures for one quantity end up in one product.

**Five guardrails survive the move to SQL because they live in code, not in a query engine.** A query engine returns zero rows for "there is nothing", "your filter removed everything" and "that question has no answer", and it will add two accounts together without a word. So: the **three empty answers** stay three different values with three different messages, from `duck.accounting_sql`'s per-clause elimination counts — one extra conditional aggregate per clause in the **same** scan, not a query per clause; **no cross-account total** exists, not even for tokens, and the refusal happens before any SQL runs; **every aggregate carries a `CoverageStatement`**; **unknown is not zero**, so `coverage.fraction` is `None` for every window that exists today and never `0.0`, which would be the claim that nobody was listening; and **plan percentages are lower bounds** over quantised, possibly-stale snapshots, a floor rather than a reading. All five are pinned, and all five are in the mutation matrix.

**The cross-account rule had one hole and it was invisible to the guard written for it.** `store.breakdown` refused before any SQL ran; `store.histogram` never asked the question at all, so `/api/v1/histogram` with no `account=` resolved `paths.ledgers(None)` to every account's ledger and emitted `coalesce(sum(cost_usd_reported), 0)` over the lot — 200 ok, no refusal, 0.2466444 over the real three-account fixture, which is exactly the per-account answers added up. The guard could not see it for a structural reason worth remembering: `test_api_no_cross_account_total_exists_in_any_payload` inspects **key names** containing "total", and a bucket's `value` is not called one, so a name-based guard cannot catch a value-based hole — and every histogram case in the suite passed `account=`. The refusal moved down into `store.py` so both callers inherit it and a third cannot miss it, and the test now asks every stream-A route its account-less question and compares against the per-account fan-out.

**Three more answers that were one answer.** An account nobody has ever seen answered 200 `no-data` with "the shipper may not have reached stream A on any machine yet" — byte-identical, bar the uuid, to the answer for a real account that has shipped stream B and not stream A, so two states produced one message and the message asserted the false one; `unknown-account` was published, and reachable on the reconciler half and unreachable on the DuckDB half. `/api/v1/values?fields=<typo>` was a 500 `reader-failed` ("a fault in the reader") quoting the generated SQL, because that list bypassed `compile_query` entirely and reached `duck._ident`, whose docstring asserted a precondition it did not enforce — `_ident` raises on an unchecked name now, and the route whitelists first. And a string value against a numeric column was **cast** rather than compared: `where.input_tokens=abc` raised into the same 500, while ` 529 `, `+529`, `529.0`, `0x12` and `1_8` all matched the integer, so a filter silently matched rows it did not name. `duck.comparable()` compiles a wrong-typed value to `FALSE`, which is exactly what the oracle's `isinstance` comparison does.

**`?account=` was joined into a filesystem path.** `os.path.join` discards its first component when the second is absolute, so `?account=/private/tmp/x` read `/private/tmp/x/ledger.jsonl`: proven against a live door, `lookup` returned a foreign row whole — model, email address, `cost_usd_reported` — and `diagnostics` returned every JSON key name in that file, one of them literally called `secret_key`. The read API is unauthenticated **by design** and that is defensible only while its contract is "every record in the store"; it is not "every `ledger.jsonl` this process can read". `Paths.stream` refuses by membership of the account list, with a realpath containment check behind it for a symlink planted inside the store, and `store.lookup` compiles the account into the query as well as into the file list so the clause survives a relaxed path check.

**NaN was a bound in both engines and they ordered it oppositely.** `float("nan")` parses, `wire._is_number` is true of it and `until < since` is false for NaN, so nothing a bound was ever checked for caught it; then Python's `ts <= nan` is False for every row while DuckDB's total float ordering puts NaN above infinity, and `until=nan` returned the whole corpus as `ok` where the declared oracle returned none. `String(NaN)` is `"NaN"`, so an omini date field that fails to parse sends exactly that. `wire.valid_pct` had the rule one file over and it was simply not applied. It is refused in `compile_query`, in `_num_param` and in `decode_cursor` — a cursor position `encode_cursor` never issued, which survives a hand edit because the fingerprint is unchanged — while `±inf` keeps working, because those are ordinary "no bound" spellings that order identically in both engines and are pinned by their own test. The differential test's shape list is what should have caught it and `nan` was not in it; `since=nan` was, in the one spelling where both engines agree by coincidence.

**`meta.store_problems` described the query history, not the store.** `DuckStore.problems` was a plain list on an object that lives for the process, appended to and never cleared: measured against a live door over a store holding exactly three unparseable lines, 1 500 `/search` requests produced 3 116 entries claiming 3 118 torn lines, the payload grew 51 kB → 1.34 MB on every response including `/health`, RSS 11 MB → 143 MB, a repaired file kept being reported until the process restarted, and a query scoped to a healthy account named another account's tear. Two entries went on per `/search`, because `_v1_search` calls `select` and then `page`. It is reset per derivation — thread-local, because the door is a `ThreadingHTTPServer` and a reset in one thread would empty another's evidence mid-answer — deduped by file with the count, and keyed `reason` like `snap.problems`, since a client rendering `p.reason` showed `undefined` for every problem this half produced. A torn `ledger.jsonl` is now named on the reader-only routes as well, from a scan of the bytes **past the last acknowledged manifest**: those are nobody's to resend, whereas a fragment *before* the door's first accepted range is the interrupted write `Store._append` terminates on purpose and is deliberately not a problem — an existing assertion says so, and the tail boundary is what keeps both true.

**The `no-data` sentence was mined from `notes[0]`, which is not an explanation.** `notes` is a list of caveats and `page()`/`breakdown()` append theirs unconditionally, so `/search` told a user whose result was empty about cursors and late arrivals and `/aggregate` told them about API list rates — while the generic sentence, whose own comment explains that it is worded to be true of both a missing and a present-but-empty ledger, was unreachable on both. It is a field on `Selection`/`Page`/`Breakdown` now, set only by the branch that can actually tell those two apart. A present-but-empty or torn-only ledger is the ordinary state of a store mid-first-write, not a corner case.

**`ignore_errors=true` has a second half and nothing counted it.** The documented half turns a malformed LINE into a row of NULLs, caught by `request_id IS NULL`. The undocumented half: with `columns=` pinned, a valid JSON line whose value does not fit the pinned type has **that value** nulled and the row kept — `input_tokens: 9223372036854775808`, `1e30`, `"abc"`, `ts: "2026-08-12T10:00:00Z"` all measured at `scanned=2, matched=2`, `request_id` intact, no counter anywhere — and `_token_nulls` then counted the row while the aggregate note said "token columns are null where the payload did not state them", a false sentence about a figure the payload stated precisely. The coercion has already happened by the time the pinned relation exists, so counting it needs a second read of the same bytes: `store.coerced_values()` is that read, a diagnostics call for `unknown_keys()`'s reason, reported at `/api/v1/diagnostics` and as a `coerced-values` store problem. What is on the query path is the truthful wording.

**The mutation harness was manufacturing its own evidence, and that is the finding that outranks the rest.** `mutate.py` copies `srv/` to a temporary tree and runs the suite against it — `srv/` alone, so `test_api_the_readme_names_exactly_the_routes_that_exist` raised `FileNotFoundError` in **every** mutated run. An exception is counted as a failure exactly as an assertion is, so every row in a 160-row matrix read `caught` whether or not anything asserted the behaviour. Three real survivors were sitting behind it: both halves of the account path check and the account clause `store.lookup` compiles. The copy is complete now (the README goes with the package) and the test fails **by name** when its input is missing rather than raising — and the two path guards are each pinned by the case the *other* cannot see, because "caught" for a pair of redundant guards is a claim about their redundancy and not about either of them. A survivor is the finding; a harness that cannot produce one is worth less than no harness, because it is believed.

**A 500 named the exception and quoted the SQL with it.** `reader-failed`'s `detail` was `"%s: %s" % (type(exc).__name__, exc)`, and several routes take caller-supplied identifiers, so an engine exception carried the whole generated statement and DuckDB's candidate-binding list to a caller this API asks no token from. The type goes on the wire; the text goes to the process's own stderr.

**`srv/ui.py` is deleted, not ported — omini is the front end, and `srv/api.py` is the contract it is written against.** A renderer shipped inside the server that produces its numbers is one opinion about them, and every honesty property it carried was expressed as *how it drew things*, which is unenforceable the moment somebody else draws them. So each is now a property of the **payload**, asserted by a test that reads the payload: `coverage` beside every attributed figure and `fraction: null` never rendered as zero; the explanation being the server's own `coverage.notes` verbatim (a fixed sentence in a client goes stale against a store that contradicts it, which is exactly what happened — a page asserting nothing emits an attestation, printed beside a strip reading `basis: attestations`); `meta.store_problems` in **every** payload rather than the diagnostics one, because a batch the reader could not reassemble otherwise makes an account render byte-identically to one that never shipped; `open` and `last_closed` as **separate keys** so a client cannot silently fall back from one to the other, with `last_sample_age_s` per account and a document-level `stale_after_s` that says outright it is a display threshold and not a measurement; and no total spanning two accounts anywhere. The three page-only tests went with the file; the ones whose other half asserted a payload kept that half, and the gauge test was **converted** into the API contract rather than deleted, which is the only reason its behaviour is still guarded at all.

**The API is `/api/v1/` and the unversioned routes are gone rather than forwarded.** Their only consumer was the deleted page, and a second envelope kept alive for a client that does not exist is ceremony that has to be tested for ever; they answer 404 naming the new base, because a 404 with no route out of it is how a client author concludes the server is broken. `GET /` is a 404 and **`GET /healthz` keeps its exact shape** — unversioned and unenveloped, because operators and scripts read that one. `--no-ui` is spelled `--no-api` and the old spelling still works.

**The envelope's discriminator is key presence, not the status code and not an empty array.** `ok`, `no-data`, `filtered-to-nothing` and `unanswerable` are a closed set, and on a refusal there is **no `result` key at all** — so a client doing `for (row of p.result.rows)` raises rather than rendering a tidy empty table, which is the exact failure ("flattening one into an empty list") the shape exists to prevent. `no-data` and `filtered-to-nothing` are both legitimate 200s. Three consequences are each their own mutation: on `no-data` the `eliminated` map is `{}` and `sole_cause` is `null`, which is `query.select`'s `if scanned and not kept` conjunction on the wire — blaming a clause for an empty corpus sends somebody to widen a filter that was never the problem; `remedy` is **never null**, on every refusal path, because a refusal with no action reads as a fault; and the `filtered-to-nothing` message quotes the engine's own clause label while the remedy names the **URL parameter** (`where.model`), since the label names the predicate and the parameter is the thing a caller can change. The mapping between the two is derived from `query.clauses_of`'s own formats rather than guessed.

**Coverage carries its tri-state in a boolean as well as a null, because a null alone is not enough.** `x || 0`, `Number(null)`, `d3.sum` and every charting library turn JSON `null` into zero without a word, and `0.0` is not "nobody said" — it is the positive claim that **nobody was listening**. So `known` is true **iff** `fraction` is non-null, both directions asserted, and `fraction` is never `0.0` while `known` is false. `basis_is` is `measured` for exactly one basis (`attestations`), and that mapping, the refusal vocabulary, the constraints and a `null_means` map from JSON path to meaning are all served as **data** at `/api/v1/capabilities` — so omini holds no copy of any of them and adding one is a one-line edit to a dict rather than a release of the front end.

**There are two coverage shapes on the wire, and the guarantee had reached only one of them.** Document-level coverage went through `coverage_payload` and was correct; per-window coverage — `windows[].coverage`, `window.coverage`, `accounts[].last_closed.<kind>.coverage` — was `coverage.Coverage.as_dict()` put on the wire raw: no `known`, no `basis_is`, and a `basis` (`unknown`, `no-attestation-names-it`, the `attestations-with-N-unreadable-span(s)` family) that no served catalogue declared. Those are exactly the rows carrying `attributed_pp` and `residual_pp`, so the object this paragraph calls insufficient was sitting beside every attributed figure in the store — and **both halves of the tri-state are live in that one slot**, because `fraction: 0.0` with basis `no-attestation-names-it` is the positive claim that an attesting host did not name this window. The deleted `srv/ui.py` did that work itself (`f === 0 && pending.length` printed no percentage at all); the rewrite moved it from the renderer into the payload and moved it for one of the two shapes. Everything the core computed still travels unchanged and `known`/`basis_is` are **added**, because a reader that reshapes a number is a second opinion about it. The parameterised basis cannot be an exact catalogue key, so it is served as `coverage_basis_prefixes`; and the suite now **derives** the emitted vocabulary out of `coverage.py`/`query.py` with `ast`, so a new basis fails here rather than reading as measured.

The blindness is worth naming because it is the pattern this file warns about twice: `_coverages()`, the walker behind both coverage tests, selected objects `if k == "coverage" and isinstance(v, dict) and "known" in v` — "every coverage object carries the boolean" written as "every coverage object *that carries the boolean* carries it". Deleting that one clause, with `srv/` untouched, turned the suite red in three places. The assertions were already right; the filter was the bug's own alibi.

**Two engines, and the split is forced rather than preferred.** Stream A is DuckDB over `ledger.jsonl` in place; stream B, the windows, the coverage and the residual are the reconciler's, because a `SELECT` over `samples.jsonl` reads neither the shipping host — which lives on the manifest, since the v1 record has no host column and `wire.sample_key` hashes the two together — nor the dedupe. A missing DuckDB is a **named 503 with the install command** on every stream-A route and never an empty result; the reconciler half still answers, so a machine without it is not a dead server. `/api/v1/window` is the one route that spans both, and it degrades per part rather than wholesale: the window's own figures come from the reconciler and the request list inside it is reported as a refusal object with **no `rows` key**, because an empty list there reads as a window with no requests in it.

Two bugs were found by building this and both were latent rather than introduced. **A `by_tag` map cannot be serialised by the door's own `json.dumps(sort_keys=True)`** — its keys are tag values including `None`, and ordering `str` against `None` raises — so any payload carrying one was a 500 over a perfectly healthy store. It was invisible because every test called the API in-process and never serialised what came back; the fix is a wire shape (`[{value, value_is_null, stats}]`, the same shape `aggregate` already used) rather than a stringified key, which would have made a request that carried no tag indistinguishable from one tagged `"None"`, and the guard is a test that runs the handler's exact `json.dumps` call over every payload. **And the histogram's bucket cap was checked only when both `since` and `until` were given**, so `interval=1&since=0` built a bucket per second from the epoch and hung the request instead of refusing it. The cap now applies to the span that will actually be filled, and `_zero_fill` carries a structural bound that raises — a cap that can be walked around is a hint, and a truncated series is worse than either a hang or an error, because it draws a complete-looking picture of part of the range.

**omini runs bundled or attached, and the server cannot tell the difference.** Bundled is a copy of the server beside omini on one machine, loopback, single user; attached is an existing omini pointed at a door running elsewhere. The server holds no session, no user and no page, so nothing about it changes between the two — what changes is who can reach the port, and that is the whole of the security difference. The read API asks for **no token** and serves every record in the store, email addresses included; the bearer token is the door's routing label for `POST /v1/ship` and nothing more. Binding a non-loopback address prints two warnings saying exactly that, and `--no-api` serves the door alone.

**Wazuh is deferred and no code exists for it.** When it arrives a Wazuh agent tails the same `accounts/<uuid>/*.jsonl` with `<log_format>json</log_format>` and nothing here changes — which is the point of the files staying the record of truth. It is written down so the next person does not add a second writer to make it possible.

**The server is published as two OCI images, and the FreeBSD one has no `RUN` instruction — that is the technique, not a style choice.** `RUN` executes a binary inside the image and a Linux kernel cannot execute FreeBSD binaries; qemu-user crosses architectures, not operating systems. `FROM` and `COPY` execute nothing, so with every package staged beforehand by `server/oci/stage-freebsd.sh` the six FreeBSD images build on ordinary `ubuntu-latest` runners in seconds, with no FreeBSD machine anywhere in CI. Adding one `RUN` does not slow that build down, it makes it impossible, and the obvious "fix" is a self-hosted runner nobody has. Everything else follows: `mkdir`/`chown` become a staged directory and `COPY --chown`, `useradd` becomes uid 65534 (which already exists in both bases — and `nogroup` is 65533 on FreeBSD, which is why the images say `65534:65534` and never a name), `compileall` becomes `PYTHONDONTWRITEBYTECODE=1`, and `ldconfig` becomes `ENV LD_LIBRARY_PATH=/usr/local/lib`. **That last one is load-bearing and reads as redundant:** FreeBSD's rtld reaches `/usr/local/lib` only through `/var/run/ld-elf.so.hints`, which `ldconfig` writes at boot; `freebsd-runtime:14.4` and `:15.1` ship no hints file, and the packaged `python3.12` has an *empty* `DT_RUNPATH` and needs `libpython3.12.so.1.0` from exactly there. Delete the line and the image builds, pushes and pulls perfectly and dies at the first exec. The technique, the `STORAGE_DRIVER: vfs` reason (overlay leaves an empty-valued `user.overlay.origin` xattr and podman on FreeBSD indexes `value[0]`, so the *pull* panics) and the absent `HEALTHCHECK` (the OCI spec has no field for one, so `--format oci` drops it while a Docker-format build keeps it) all come from `gabrielbelli/freebsd-oauth2-proxy-oci`, which is the user's own repository and sets the convention. **Nothing `buildah` builds has ever existed and the whole workflow has executed nowhere** — but the FreeBSD image itself HAS been built, and the first draft of this paragraph said it had not. `docker build --platform freebsd/amd64` produces it on a macOS/arm64 machine in about 5.5 s, config `freebsd/amd64`, nine labels correct, no health check, uid 65534, `LD_LIBRARY_PATH` set, 5 263 members carrying the server, FreeBSD CPython and `py312-duckdb` and none of the workstation half. That is the no-`RUN` technique's whole claim, demonstrated rather than argued. What it does **not** touch is everything that is specifically buildah's — `--format oci` dropping `HEALTHCHECK`, the `--annotation` flags, and the `STORAGE_DRIVER: vfs` xattr trap — nor running the thing, which needs a FreeBSD kernel nobody here has. `buildah` and `skopeo` are absent from that machine with no Darwin build to install, and `podman` is a client with no machine. `server/README.md` separates the built-and-inspected list from the never-run one rather than letting a green table imply the middle step happened.

**Its `pkgindex.py` resolves a closure where the reference refuses one, and every difference is a refusal that had to become a walk.** `verify` and the z-base-32 alphabet carry over unchanged — the checksum is the part that would fail silently if it were wrong — but `find`, which aborts the moment a package declares any dependency, is replaced by `resolve`, because CPython and DuckDB are a graph. Four things there are refusals rather than skips, and each has a published-image failure behind it: a dependency absent from the index (a missing library), a `--without` name that is not in the closure (an exclusion list that silently stopped applying, restoring 898 MiB to an image whose README says it does not carry it), an unsupported checksum version, and an index that parsed to nothing. `shlibs`, `arch` and `modules` are new: **the base and the package ABI are one matrix row and crossing them is silent at build time**, because nothing executes — 14.4 ships `libutil.so.9` and 15.1 ships `libutil.so.10`, so `shlibs` walks every `DT_NEEDED` in the staged tree against the unpacked base and refuses by name, and `modules` derives the import list from `srv/` with `ast` so the 183 MiB prune cannot take something the server needs. **DuckDB is packaged for FreeBSD** (`py312-duckdb`, at exactly the pinned 1.5.5 on every target ABI), so the image is full-capability rather than degraded — but the pin works the other way round from Linux's: `pkg` has one version and no way to ask for another, so CI compares what it resolved against `ARG DUCKDB_VERSION` and fails, where the Linux build *requests* a version and proves it by importing it. The numpy/pandas exclusion is four pieces of static evidence and **no measurement on FreeBSD**; the smoke job is what closes that, and `server/README.md` lists what is unverified rather than glossing it.

**The package index was the root of trust and nothing verified it.** `fetch-pkgs.sh` fetched `packagesite.pkg`, extracted `packagesite.yaml` and derived everything from it — the URL each package is downloaded from (`repopath`) *and* the blake2b digest it is then checked against (`sum`). So "verifies every blake2b checksum", asserted in `server/README.md`, in `Containerfile.freebsd` and in the workflow, meant only that the bytes matched what the same unverified document said they would: substitute the index and both halves move together while every check passes. It needed no new dependency, because the archive already **contains** what closes it — three members, and the script extracted one and discarded `packagesite.yaml.sig` and `packagesite.yaml.pub`. `pkgindex.py verifyindex` pins FreeBSD's own repository fingerprint (`sha256(packagesite.yaml.pub)` = `b0170035…f438`, from `/usr/share/keys/pkg/trusted/pkg.freebsd.org.2013102301`) and does RSA-2048 PKCS#1 v1.5 in ~25 stdlib lines, the same register the ELF reader is written in. Two details are load-bearing and both were **measured against the live index rather than assumed**: pkg signs the ASCII **hex string** of the file's sha256, not the digest — the plain hash was tried and does not verify, so a reader "simplifying" that gets a check that can never match — and the recovered block is compared against a **reconstructed** one byte for byte rather than searched for a DigestInfo, because a `find` accepts short padding with attacker-chosen bytes in front. Both are pinned by mutation, the second with a forged block a test can only build because it holds a synthetic private key. The same fetcher now passes `--proto '=https' --proto-redir '=https'`: `curl -fsSL` follows an https→http redirect silently, which is the cheap way to author both the `repopath` and the `sum`.

**Every published image made three claims about itself that were not true, and one of them was a hardcoded capability.** `org.opencontainers.image.licenses` said `MIT` in three places while the image `COPY`s this project's BSD 2-Clause `LICENCE` a few lines above the label — the reference repository's licence copied without re-checking, in a field SBOM and compliance scanners read as authoritative. `image.version` on the FreeBSD half was `${DUCKDB_VERSION}`, so a release that had just asserted the git tag equals claudio's `VERSION` published an image annotated with a third party's number. And `com.claudio.stream-a="available"` was a literal on the image that has never been executed anywhere, while the image whose engine is imported and version-asserted on every build carried no such label — so anything keying on it read the proven image as not-available. It is **deleted rather than corrected**: there is no `RUN` in that build to derive it with, a directory existing is not a module importing, and `:testing` publishes even when the smoke job fails, which covers amd64/15.1 alone. Engine availability is a run-time answer in one place. The guard could not see any of this because `test_oci_the_two_images_offer_the_same_contract` — whose docstring is "Interchangeable, or the operator learns two things instead of one" — compared `ENTRYPOINT`, `USER` and `EXPOSE` and nothing else; it now diffs the two **label key sets** and derives the expected SPDX identifier from the repository's own `LICENCE` file.

**A tag is not immutable and the file said it was.** `sha-<short>` was documented as "the only tag here that can never be re-pointed" and "what a deployment pins"; a registry tag is mutable by anyone with push rights and the workflow re-points it itself on any re-run at the same commit — which need not produce the same bytes, since both base images and the FreeBSD `latest` package branch float. Worse, the manifest job resolved those names **by name** minutes after they were pushed, and the concurrency group is per-**ref** with `cancel-in-progress: false`, so a branch push and a tag push at one commit are two unserialised runs writing the same names, either able to assemble `:testing` and a release list out of the other's images. Every build job now captures the digest its push returned, writes it into the marker file the manifest job already discovered targets from, and the lists are assembled from `@sha256:…`. The same digest is what `actions/attest-build-provenance` attests — which the workflow had none of, on an artefact whose authenticity is the only integrity control in a chain with no TLS, no token expiry and no rate limiting anywhere. The bases are pinned the same way and for the reason the file already argued at length for GitHub Actions: `python:3.12-slim-bookworm` was measured moving between 2026-08-13 and 2026-08-21, and it is the largest executable input in the image. `--password-stdin` in all three logins, not two of three: log masking hides a secret in output and does nothing about argv.

**`/api/v1/window` returned no response at all for the ordinary case, and the fixture was the bug's alibi.** `_wire_window` ran `by` and `by_tag` through one loop, and they are different shapes — `_buckets` is nested `{dimension: {value: stats}}` and `_tag_buckets` is a flat `{"k=v" or None: stats}` — so the tag *values* were iterated as dimension names and the result stayed keyed by `str` and `None` together, which `json.dumps(sort_keys=True)` cannot order. The handler raised and the client got the connection dropped: HTTP 000, below even a named 500, on any window holding both a tagged and an untagged request. A test written for exactly this bug, naming it in its docstring and calling the right route, passed over it for as long as it existed, because all three of `alpha`'s captured rows carry `tags: {}` and the one tagged row in the whole corpus belongs to `agent`. The mixed case was real data that was never asked for; nothing was fabricated to fix it, and the probe beside it asserts the chosen window really carries both bucket kinds so the guard cannot go quietly vacuous again. Beside that, `/window` published a **placement census of zeros** for the rows it had just refused to read — `rows_total: 0`, `windows.touched: 0` about the window on the same payload, and `basis: "no-window-touched"`, a positive claim — byte-identical to the answer for a window that genuinely holds no requests, while `/api/v1/windows` reported the true `rows_total: 3` for the same account at the same moment. Coverage is a refusal object there now, with no numbers at all, and the decision lives on one line so a single mutation can restore the bug.

**`/healthz` is the only surface served before reader auth, and it did not name the engine.** `/api/v1/capabilities` and `/api/v1/health` both do and both need a token — and `readers.json` is not exotic, it is the only configuration `serve()` permits on a non-loopback bind, i.e. every container. Measured: the key sets of an engine-present and an engine-absent door were identical, so the health check this repository's own README recommends reported **healthy** for a door whose entire stream-A half refuses every question. Both files also claimed `/api/v1/health` asks "the same question as `/healthz`", and they differed on precisely the property that decides whether half the API works. It is one line in `Door.health()` and it is additive, so the shape the README calls exact is unchanged.

**Layered config.** Three files share one `key=value` line format, read line-wise and never parsed into structures: global `$CLAUDIO_CONF`, profile `claudio.conf`, project `.claudio.local`. Last value wins per key; `tag=` is the one repeatable key. `claudio.conf` is deliberately **not** in `CONFIG_MAP` — it configures claudio, not Claude Code, so it must never be symlinked into a project. Resolution is centralised the same way: one helper per axis (`_resolve_account`, `_resolve_tags`, `_telemetry_conf`), and `_build_env` is the single place that turns them into `NAME=value` lines. Note the asymmetry — `_build_env` calls `_resolve_tags` and `_telemetry_conf` itself, but the account is resolved *and validated* earlier, by `_run_prelude`, and only its result is passed in; see the first trap below for why that is not an accident. `_conf_set` is the matching writer, shared by `default` and `account default`. `_resolve_tags` read only two of the three layers until recently — a machine-wide `tag=` was silently dropped while every doc promised it, the silent-success class of failure this tool exists to avoid — so the global read now sits in the emit block, and **its position is the whole of its correctness**: below the profile line a global tag would beat a profile's, inverting the layering for one key while `account=` kept the other order; above the auto block the automatic `host=`/`email=` would beat a global `tag=host=`, breaking the bottom-layer promise the readme makes. Both wrong slots look plausible and neither is caught by any pre-existing assertion, so the tests pin ordering against a same-key tag in the neighbouring layer rather than merely asserting the global tag appears. Telemetry is **opt-in** — the exporter block appears only when `logging=` names `local` or `remote` — and it is the one axis with no environment layer: where telemetry goes belongs to the machine and the project, not to one shell, so `--no-telemetry` is the only per-run override and it can only switch it off.

**`logging=remote` ships now, and the note it carries is no longer "nothing ships" but every state in which it looks like it does.** `remote` was parsed and reserved for a release, with `readme.md` saying "recorded **and** shipped" on the worked example for the one use case the mode exists for — a user believing their employer receives records that were never sent, this project's cardinal sin on the highest-stakes key there is. `usage/cu/ship.py` is the uploader, and the caveat is replaced rather than deleted, because the same failure has three new shapes and all three are silent without it: **no account resolved** (destinations are keyed by account, so none can be found), **no `ship_url` for the resolved account**, and **a `logging=remote` that came from a project or profile file**, which the shipper cannot honour because it is a machine-wide receiver with no cwd and no profile and therefore reads the mode from the global conf only. Silence is reserved for the configuration that actually works, which is what makes the silence readable. Appended rather than assigned, because a deprecated key being retired in the same breath is a separate thing the user has to hear. The suite pins all four shapes and the negative (`logging=local` says nothing) — and note that the two pre-existing assertions, "`logging=remote` implies local, so stream A is on too" and its stream-B twin, would both still pass if `remote` were deleted from the parser and aliased to `local`, which is why they could not catch the original.

**The shipper is a tick inside the receiver, and every part of what it refuses to do is load-bearing.** `usage/cu/ship.py` runs from `otlp-recv`'s watchdog and once more, unconditionally, in the `finally` before idle exit — no cron, no launchd, no systemd, for the same three reasons the receiver itself is not a service. The final pass is not a nicety: the tick is up to `check_seconds` behind, so without it everything written between the last tick and the exit waits for the next session to start a receiver, which on a machine that ships once a day is a day. Five decisions carry it:

- **The destination fails closed, and there is no plain key to fall back to.** `account.<name>.ship_url` and `account.<name>.ship_token` are read from the **global conf only** — `_ship_conf` on claudio's side, `ship.destinations` on the shipper's — and that is `_telemetry_conf`'s account inversion with the fall-through *removed*. A `.claudio.local` in a repository someone else wrote must never be able to name where this machine's telemetry is posted; and a machine-wide default destination is worse still, because one `usage_dir` holds every account's records interleaved (the real capture is three accounts in eight rows) and a default would publish two personal accounts to an employer. Both halves are refusals: a `ship_url` under `logging=local` ships nothing, because shipping on the presence of a URL would make `logging=local` upload records — the same sin pointed the other way.
- **A row is placed by identity, never by label.** Stream B carries `account_uuid` and is matched on it exactly. Stream A carries no UUID at all, so it is matched on the `email` tag against the address in that account's own `.claude.json` — the same file the UUID is read from, so both sides of the match come from one source — and the UUID is then stamped on, here, because D9's whole point is that the mapping is readable on the machine and nowhere downstream. `account` is a user-chosen label `--tag account=` overwrites and is never matched on. Measured: the email match places 8 of 8 real rows into the right one of three accounts; the alternative join, `session_id` against stream B, places 7 of 8 and leaves the `sdk` session unplaceable **for ever**, because a session that never moves the plan percentage produces no sample — and an unplaceable row at the head of the file would jam the offset behind it. A row that names nobody is the third answer: not shipped, and counted into `ship.warn`. The honest limit is stated in the code rather than buried: `email` is a resource attribute, so a `tag=email=` line in a repo's config file could misplace a row. The destination cannot be redirected that way; the selection can. Closing it needs an identity Claude Code emits itself, which it does not today.
- **The wire format IS the file format.** A stream-B line is POSTed byte for byte; a stream-A line is its bytes with one key **spliced in textually**, so stripping the suffix gives the file back exactly and a captured body is diffable against `ledger.jsonl`. `json.dumps(json.loads(line))` would also produce valid JSON, and would reorder keys, reformat floats, re-escape non-ASCII and drop any key a future Claude Code adds before this reader learns about it — a third schema, invented in transit, with nothing to compare it against. The stamp's value is regex-guarded rather than escaped, because a UUID that could carry a quote into the splice is not a UUID.
- **The offset advances only on an acknowledged write, and it never jams.** A refused POST changes nothing at all, so the next tick resends the identical byte range — safe because both streams dedupe server-side (`request_id`, `wire.sample_key`), which is the same property `start_offset` already relies on. A range that held only *other* accounts' rows still advances, because that is a final decision and not a deferred one. A final line with no newline is a write in progress: not shipped, not consumed, not counted as malformed. `file_identity`/`start_offset` are **imported from `cu/tail.py`, not reimplemented** — they were moved there the moment a second reader needed them, because a second implementation of exactly this is what put 57% of a machine's captured spend permanently out of reach, and the test asserts the two are the same function object rather than two that agree today.
- **`raw/` is never read, structurally.** It is larger and it can hold prompt and response bodies (`OTEL_LOG_USER_PROMPTS` is the user's own opt-in and the receiver does not redact). A test asserts the source never names `raw_file`/`raw_dir`/`raw_files` outside a comment, *and* that a payload sitting in `raw/` never appears on the wire — the static half alone would pass a shipper that reached it by another name.

**Four silences in the shipper, and every one of them read as health.** They are listed together because they share a shape: a state the file's own docstring claims to make unreachable, reached quietly.

- **`place_row` has three answers and only two were counted.** `None` (no `email` key) incremented `unidentified`, `True` shipped, and `False` — the row names an address no destination has — fell through `if not placed: continue` with no counter while the offset advanced past it and was durably saved. So a valid, configured destination could consume the whole ledger and report `destinations: 1, posts: 0, unidentified: 0, refusals: [], failures: []` with neither file on disk. Two of the three ways in are documented user actions: `tag=email=redacted`, which every doc offers as the way to suppress the PII tag and which leaves `email` a *non-empty string*, and an account re-logged under a new address. The count is now `report.unplaced`, decided **once per pass** and deduped on `request_id` — a row is unplaced only if every destination refused it, which cannot be decided inside a per-destination scan — and a destination that has scanned bytes and placed nothing is named with both addresses. More importantly the ledger offset is **not advanced** for it, which is the `partial` branch's rule applied to the case that takes the same damage: scanning would consume rows that become placeable the moment the address agrees. The ordinary multi-account ledger is the negative that keeps the alarm readable — other accounts' rows are unplaced by design and say nothing, because that destination placed rows of its own.
- **`ship.warn` was erased by the next tick.** Its two counters describe only what *this* pass scanned and the offset moves past the offending lines, so pass 2 counted zero and unlinked the file: "these rows will never be shipped" lived about fifteen seconds, and both readers (`claudio run` at session start, `doctor` on demand) are outside that window in practice. `ship.err` never had the problem because a failed POST leaves the offset alone and re-reports every pass — the warn file is the one whose condition is by construction *non-repeating*, which is why it is the one that had to persist. The counts accumulate in `state/ship-unplaceable.json` and the message is re-derived from the running totals every pass; it clears when the totals are gone, which means when somebody deleted the file. An acknowledgement, rather than a timer.
- **An unreadable file answered *success*.** `file_identity` returned `None` on any `OSError`, so EACCES, EIO and a stale mount were all "no such file yet" — which contributes to no failure list, so the next pass reached `clear_ship_error` and deleted what the previous one had reported. `chmod 000 ledger.jsonl` ended shipping for good with every diagnostic surface clean. `file_identity` now returns `None` for ENOENT only and raises otherwise; `file_identity_quiet` is for the callers whose next step reports its own read failure (ingest hands the path to `otlp.read_file`), so the fix could not turn a counted skip into a traceback out of a command.
- **The ack was never read.** `post_batch` read the response body on neither path, so a 507 `disk-nearly-full` with `detail: "N bytes free, reserve is M"` arrived as `HTTP 507` and a 409 `identity` — the shipper aimed a file at the wrong destination, and that one jams the stream for ever because the offset never advances — arrived as `HTTP 409`. The door's docstring calls those "the two numbers that go wrong invisibly". Both now reach `ship.err`, and the `offset` in every 200 is compared with the one this machine is about to store: they are equal in the steady state, because the door stores `max(prev, to)`, so a disagreement is real and is named.

**`reset` on the manifest is the client's signal, and only the client can compute it.** `_ship_stream` detects `start > size` and re-reads from zero, but an in-place rewrite that keeps the first 256 bytes leaves dev, ino and the head hash unchanged, so the door recognised the resent range as one it already held and dropped the batch with a 200 — while the client advanced its own offset on that 200.

**The identity triple is not enough on Linux, and the anchor is what makes it enough.** `(st_dev, st_ino, head)` answers "is this the same file", and on Linux it answers wrong in the one direction that loses records: inode numbers are reused immediately, so a file unlinked and rewritten at the same path takes its inode back, and the first 256 bytes of an append-only file rebuilt from its own start are unchanged **by construction** — all three fields match a file that is not the one the offset describes. Measured with the same six lines on both platforms: macOS returned a new `ino` for the replacement, Debian returned the identical triple. The consequence is exactly the 57%-of-spend silent skip that `start_offset` exists to prevent, on the platform a shipping host actually runs, and it was invisible on the author's Mac — `test_ship_resumes_by_offset_and_rescans_a_replaced_file` was green there and red in a Debian container, which is how it was found. So the offset now carries `anchor`, a hash of the 256 bytes immediately *before* it: what the reader had just consumed when it stopped. If those bytes are not there any more, the file under the offset is a different file whatever its inode says. It costs one 256-byte read per file per pass, it is computed **after** the read because it describes bytes that were read, and "cannot vouch" — offset 0, unreadable, or a file now shorter than its offset — reads as a restart and never as a pass. `path` is a **required** positional on `start_offset` for that reason: an optional one would let a caller drop the check by omission and still get a plausible offset back. An offsets file written before anchors existed restarts once, named, which is the legacy-integer rule one field along. Nothing changed on the wire — the manifest carries `file_identity`'s triple as it always did — because the client detecting the replacement is precisely what makes it set `reset`, so the paragraph above is the mechanism this fix *uses* rather than one it replaces. Same evidence, opposite failure direction: here re-reading costs a parse, there discarding costs the records. The key is optional and absent means false, so a shipper written before it existed is still accepted; present and not a boolean is refused by name, because a value a write-or-drop decision rests on is validated like one.

**`ledger.append` glued a good row onto a torn fragment.** A process killed mid-append leaves a line with no newline and the next append wrote straight onto it, so one fragment plus one good row became one unparseable line: `read` counted `malformed: 1`, the row was gone, the raw offset had already advanced past its source, and `ship._select` consumed the same bytes and advanced past it too. `serve.Store._append` has had the guard from the start and says why — "instead of gluing a fragment onto the front of a good record and costing two" — so this is that fix on the other end of the same wire, with the tear still counted rather than painted over, plus an `rfind` recovery in `read` for the lines already on disk. And the ingest seam is now fsynced in the order it is written: `ledger.append` syncs its bytes before `tail.save_offsets` renames the file that accounts for them, because a rename is journalled metadata and an append is not, and the raw file it came from is rotated away.

**The receiver releases the socket and the pidfile before the final shipping pass, not after.** `serve_forever` has returned, so nothing is being served — but the socket was still bound and `recv.pid` still named a live pid, which is exactly what the supervisor's `kill -0` and `claudio run` read as "up, export away": measured at 0.7 s after SIGTERM, with a POST dying `ConnectionResetError` 3.3 s later, records Claude Code drops in silence. Before the shipper existed that window was two file writes; it is now a network call bounded only by `TIMEOUT × MAX_BATCHES_PER_PASS` per destination per stream. Socket first so a replacement can bind, pidfile second so the supervisor spawns one, data last. Pinned behaviourally against a blackhole destination, which is the only shape that can catch it.

`ship.err` and `ship.warn` are the recv pair one layer out and split for the same reason: `ship.err` means nothing was delivered (the offset is untouched, so it is a retry rather than a loss) and `ship.warn` means delivery worked but some records can never be placed. `claudio run` prints both, from `_run_receiver` **above** the protocol gate — shipping does not depend on this machine's receiver, so someone exporting to their own collector ships from the same ledger and never reaches `_recv_ensure` at all. `ship.tick` swallows every exception and writes down what it swallowed: a traceback escaping into the watchdog thread would end the tick loop, and with it the idle exit and the session sweep, leaving a receiver that runs for ever for a reason nobody can see.

Three things the shipper deliberately does not have, because they were scoped out rather than forgotten: the bearer token is a **tenant label for routing** and is not engineered as a security boundary (no mTLS, no CA, no rotation — the network is treated as already trusted); there is no PII policy engine, no pseudonymisation and no aggregate-only mode, because per-account destinations already separate work from personal and the rows are the product; and there is no backup, retention or disk-growth machinery at all — `usage_dir` is append-only files and pruning them is the operator's job, which `readme.md` says outright.

**The door is the shipper's other end, and it decides five things and no more.** `server/srv/serve.py` — stdlib `http.server`, `POST /v1/ship`, NDJSON, optional gzip — is where the bytes land. It is the one impure module in `srv/` and is named in the purity test rather than hidden from it. What carries it:

**`tokens.json` is the one file an operator has to write, and it was documented nowhere.** The door starts with no token → account mapping and answers `401` to every batch until it has one; it says so on stderr, twice, on every start. Following `server/README.md` literally therefore produced a door that accepted nothing, named a file the README never mentioned, and left the reader with nothing to create — the whole shipping path (`logging=remote` → `ship_url` → this door) failing at the one step that cannot be guessed, with both ends of the wire unstated as well: where the account UUID comes from (`.oauthAccount.accountUuid` in that account's own `.claude.json`, which is where the shipper reads it too, so the two ends have one source) and which config layer the client reads the destination from (global only). The section is pinned by a test that **derives** the filename and the override flag from `serve.py`'s own argument parser, so renaming either fails there rather than leaving the README describing a file that no longer exists.

- **The token names the tenant; the body never does.** A record whose `account_uuid` disagrees with the token's fails the **whole batch** with 409 and nothing is written, because a batch is one byte range of one file on one machine — a disagreeing record means the shipper aimed the file at the wrong destination, and the agreeing records in it are no more trustworthy than the rest. The rule is `ingest.Batch`'s rule spelled a layer earlier, and it is spelled *exactly*: a record naming **no** account is accepted here and refused downstream by name (`no-account-uuid`), because a door stricter than the core would jam a client's offset for ever over a batch the core would have taken.
- **Durable before the ack.** Records appended and fsynced, then the manifest, then the offset by temp+rename with the directory fsynced, and only then the 200. `F_FULLFSYNC` where the platform has it, because on Darwin `fsync` returns once the data reaches the drive's cache and "durable" then means "survives the process", not "survives the power". Nothing is ever partially acknowledged, so a client that does not get a 200 can always resend the same bytes.
- **It computes nothing.** Each line is parsed once — the identity check demands it — and then the line's **own bytes** are appended. Every interpretation is `reconcile.py`, re-derived from byte zero, which is what lets a week-late shipment retroactively correct a closed window.
- **The manifest is stored beside the records, and that is not bookkeeping.** `wire.sample_key` hashes a stream-B record *plus the shipping host*, and stream B's v1 shape has no `host` column of its own — 65 real records are in that shape — so a door that kept the records and dropped the envelope would make them unattributable to any machine, silently and for ever. Each accepted batch appends the manifest's own bytes with a `"recv"` object **spliced in** (`cu.ship.stamp`'s trick, one hop on) naming the byte range those records occupy, and `read_batches` turns the pair straight back into the `ingest.Batch` the core consumes.
- **The ack carries the two numbers that go wrong invisibly**: the client offset the door durably holds, and the store's free bytes — in every response including the refusals, with a 507 once a batch would take the filesystem under the reserve. A number that only appears once it is too late is not a warning.

Two consequences worth keeping. A range the door **provably** already holds — same client file identity, `to` at or below the held offset, **and no `reset` claimed by the client** — is skipped rather than appended, and a range it does *not* know it holds is appended again and deduped by the core; the second is the important half, because refusing to write something already written would be a wager on an offset that may not have survived. The skip is counted as `batches_skipped_as_held` and not as a duplicate, because a discard and a duplicate are the same event only when the door is right, and `/healthz` is where an operator has to be able to tell them apart. And a `from` **above** the held offset is not an alarm: `cu.ship._ship_stream` advances over a byte range that held only other accounts' rows without posting anything, so a forward jump is the everyday state of a multi-account ledger and flagging it would be a warning written from an assumption. What the door does not have is the shipper's list one file on: no TLS, no mTLS, no CA, no token expiry, no rate limiting. `server/README.md` says once, plainly, that it is for a trusted network and must not face the internet, and the process repeats it on stderr whenever it binds a non-loopback address.

**A value `logging=` does not know retires the old keys too, and that branch is where the retirement notice was jumped over.** The unknown-value case sets `_LG_MODE=none`, writes its own note and `return 0`s — and that return used to skip both the `if [ -z "$_LG_MODE" ]` fallback *and* the `elif [ -n "$_lg_old" ]` retirement notice, so `logging=lokal` beside a working `otel=1` silently killed the export and said only "claudio does not know that value". The reasonable reading of that message is that the previous configuration still stands. It does not. The clause is **appended inside the branch**, deliberately not reached by falling through to the `elif`: that `elif` replaces the note wholesale and names `logging=none`, a mode nobody wrote. Both wrong shapes are pinned separately, because the naive fix passes the test written for the original bug.

**`_telemetry_lookup` is the one search order; `_telemetry_conf` is a thin reader of it.** It prints `<where>\t<value>` — the phrase naming the key, the value and the file that decided — because a *verdict* that respects the account inversion and a *remedy* that does not is still a lie: `Recording is off. Turn it on with: logging=local in <global conf>` was printed at a user who had exactly that line in exactly that file, beaten by an `account.<name>.logging=none` in the same file. They edit it, re-run, get the identical message, and can never reach the layer that decided. `_logging_resolve` takes the layer into `_LG_WHY` from the same lookup, so this costs no extra pass, and both report paths print it in place of the generic remedy.

**Anything that reports recording must resolve `usage_dir` as well as the mode.** `_statusline_recording` answered from `_LG_USE` alone, while the shim blanks `_U_DIR` when the resolved `usage_dir` is inside `$HOME/.claude` and the run path returns on the same condition — both silently, by design, because an empty `_U_DIR` is what everything downstream reads as "nowhere to write". So `claudio statusline` printed `Recording plan usage: on (logging=local)` while nothing was ever written, for ever. The refusal is right; the silence was not, and the one command whose job is to report the state of recording is the wrong place to be quiet. It now sets `_SL_REC_WHY` and both report paths print it; and `_run_receiver` checks the directory **above** the protocol gate and says so on stderr, because the refusal costs both streams, not just the receiver.

**`logging=none|local|remote` is one key where there were three, and `remote` implies `local`.** A remote-without-local mode was considered and dropped: it saves a rotating 32MB file and buys a state in which a healthy setup is indistinguishable from a broken one. `_logging_resolve` is the single resolver — it sets `_LG_MODE`, `_LG_OTEL`, `_LG_USE` and `_LG_NOTE`, layering through `_telemetry_conf` so the account inversion, the global-conf-only rule and the `--no-telemetry` override are all inherited rather than re-implemented. A value that is none of the three is **off and named**: guessing `local` turns on something nobody asked for, and guessing `none` in silence is the loss this project calls its cardinal sin.

**The deprecation is where the silence would have been, so it is the loudest part.** `otel=` and `usage=` are read for one release. With no `logging=` anywhere they still decide, *independently of each other* exactly as before, so an existing machine behaves identically across the upgrade. The moment a `logging=` line appears anywhere, it retires the old keys **everywhere** — every layer, account-level ones included — and every retired key is named on stderr on every run until it is deleted. That is one rule rather than a per-layer merge on purpose: a merge leaves a config in which some old lines still bite and some do not, which nobody can reason about, and the direction had to be the one that cannot make `logging=local` quietly do nothing. It has a real price, stated in `readme.md` rather than buried: an `account.personal.otel=0` stops applying the moment `logging=` is written. The note is printed **above** `_build_env`'s `--no-telemetry` return, because a config file that is going to stop working is not a telemetry setting and silencing one run's export must not silence it. `LOGGING_LEGACY` names the retired keys in one place, and the doc guard derives the list from it — a hardcoded copy in `test.sh` would be a third place to forget.

**Per-account logging inverts the layering, on purpose.** `_telemetry_conf key profile account` reads `account.<account>.<key>` from the **global conf only**, and that value beats project, profile and the plain global key alike. Every other resolver goes broad to narrow; this one does not, because a privacy choice attached to an identity must not be overridable by a file inside a repo that anyone may have written — `account.personal.logging=none` is a guarantee, not a default. `--no-telemetry` still wins (the check sits above the `otel` lookup in `_build_env`), and with no account resolved the layer is skipped, so behaviour is exactly what it was before accounts. No parser change was needed for the dotted key: `_conf_values` matches with a *quoted* `case` pattern, so `account.work.otel` is a literal — `otel=` and `account=` lookups cannot see it, and an account named `*` cannot inject a glob. Unknown `account.<x>.<key>` keys are inert by design: `_telemetry_conf` is reached from inside `_build_env`'s `$( )`, where an `exit` would be swallowed.

**The update check buys its place with two costs it refuses to pay.** `claudio run` never waits on the network and never nags: `_update_notice` reads one stamp file (`~/.claudio/update-stamp`, derived from `GLOBAL_CONF`'s directory so overriding `CLAUDIO_CONF` moves it and the suite stays hermetic for free), and if `checked=` is over 24h old it forks a detached refresh and carries straight on. `notified=` is what makes a new version announce itself **once per version** rather than once per run. The feature is opt-in with three states in `update_check=` — unset means "offer once, on stderr, never prompt", `1` enabled, `0` declined and never mentioned again — and `offered=` lives in the stamp rather than the conf because the conf is the *user's* file: claudio does not scribble a three-state choice into it. `CLAUDIO_UPDATE=0` is the hard kill switch, checked before any file is opened, and every test wrapper but `run_upd` sets it. Version detection reads the filesystem rather than asking a tool: a claudio under `.../Cellar/claudio/<version>/` defers wholly to brew (installed version = the directory name, available = the tap formula under `Library/Taps/`), because `brew --prefix` is Ruby and takes ~2.9s against 0.007s for two path reads; anywhere else the embedded `VERSION` is compared against `git ls-remote --tags` — no clone, no auth, no `gh`. `_ver_gt` is dotted-numeric awk because BSD `sort` has no `-V`. **The repo has no tags yet**, so `_latest_tag` returns empty for everyone today, and empty must print "no releases tagged yet", never "up to date" — a check that claims good news on no evidence is one nobody believes later.

**Why accounts are environment, not directory state.** The account is process-scoped by design. Recording it beside `.claudio` would make it a property of the directory, and two terminals could no longer run the same project under different accounts. Nothing about an account or a tag is symlinked or written as active state; it lives only in the environment of the `exec`ed `claude`. `claudio default` writes *defaults*, not state, to `.claudio.local` — personal and gitignored — in contrast to `.claudio`, which names the project's profile and is shareable.

**Why the storage moved.** claudio used to keep its profiles, accounts and global conf inside `~/.claude` — squatting in Claude Code's own directory, whose layout is Claude Code's to change. claudio's data was indistinguishable from its host's, rode along with anything done to that directory, and could be displaced by a name Claude Code wanted next. It now keeps a directory of its own, `~/.claudio`; only the *storage* moved, never `CONFIG_MAP`'s in-project targets (`.claude/settings.json`, `.claude/hooks`, …), which are Claude Code's project layout and are not ours to change either.

**`migrate` — temporary, and scoped so it can be deleted in one commit.** The whole migration is `LEGACY_DIR`/`LAYOUT_CUSTOM` at the top of the script, the `# --- migration ---` block near the bottom, and three calls to `_legacy_hint` (`cmd_list`'s empty branch, `_require_profile`'s not-found branch, `cmd_clean`'s zero-removal branch). Delete them together after two releases. It is a subcommand rather than a loose script in the repo because what is installed is `bin/claudio` plus `libexec/claudio/`, and a loose script in the repo is in neither: it isn't undiscoverable, it is *absent from the affected machine*.

Two facts drive its design, and neither is inferable from claudio's own source:
- **On macOS the login is not in the account directory.** Claude Code derives its Keychain service name from a hash of the config dir path (`Claude Code-credentials-<sha256(dir)[0:8]>`), so moving an account orphans its credential; on Linux the credential is a file inside the directory and moves with it. Hence the platform-conditional `LOGINS:` block, printed *before* the confirmation prompt, and hence `--undo` being genuinely useful rather than a nicety — the name is a pure function of the path, so moving back restores the login. **Be honest about the asymmetry in evidence here:** the macOS half was observed; the Linux half is Claude Code's documented behaviour and **has never been run on Linux** — the `!= Darwin` branch is reached in no test on any developer machine so far. The move itself is platform-neutral (`mv` and `ln -s`, no credential is ever touched), so what is unverified is the *advice*, not the migration. If it turns out to be wrong, the symptom is a user told no re-login was needed who then needs one, and the fix is `claudio account login <name>`. Do not quietly upgrade the claim to tested; `readme.md` carries the same caveat and the two must stay in step.
- **Moving the profiles dir does not dangle a project's links, it disowns them.** `_is_claudio_link` matches by prefix, so after the move `clean` reports success removing nothing and `use` reports success relinking nothing. Re-running activation therefore *cannot* repair a project, which is why `migrate` rewrites link targets in place, matched by target prefix rather than through `CONFIG_MAP` — a claudio link can sit at a path `CONFIG_MAP` never mentions, and nothing else will ever come back for it.

A third fact was found by testing rather than reasoning, and it is the one most likely to be undone by a well-meaning refactor: **`migrate`'s intermediate lists are tab-separated and nearly every field in them is a path, so a tab in a path is a delimiter collision, not an exotic input.** With the link path in the first field of `_links_under`'s output, a symlink named `notes<TAB>x.md` was read back as the link `notes`, and the repoint did `rm -f notes` — deleting an unrelated file of the user's, writing a junk symlink over it, and exiting 0. The invariant now: **a field that can contain a tab is either last on its line or alone on it.** `_links_under` emits the link path and nothing else (the caller re-reads the target with `readlink`, which needs no delimiter); `_mg_work` is `<count>\t<dir>`, count first; `_mg_repoint` is `<state>\t<detail>\t<link>`. Where no safe ordering exists — `_mg_items`' line is three paths — the item is refused **by name** instead of mangled, and a newline-named symlink, which `find` cannot report atomically at all, is warned about rather than passed over. Silence is the one unacceptable outcome: the entire promise of the command is that no link is left dangling without a word.

The plan is also required to be **predictive, not just descriptive**. Destination collisions are computed with `[ -e ]` before anything is printed and shown inline as `CONFLICT`, because `--dry-run` exists precisely so the user sees a refusal while it is still a preview; discovering it afterwards on stderr is too late to be a plan. Symmetrically, the closing summary is conditional on `_mg_rc`: when every move was refused, the unconditional "claudio's profiles now live in `<new>`" was a plain lie on stdout with its only contradiction on stderr, so `claudio migrate 2>/dev/null` sent the user away believing a migration had happened.

Consequences worth keeping: moves are **per item**, never per parent (`mv old/profiles new/profiles` nests into `new/profiles/profiles` when the destination exists) and guarded by an explicit `[ -e ]` (`mv` refuses a non-empty destination directory but silently replaces an empty one); a profile whose move was refused is recorded in `_mg_blocked` so its still-working links are left alone instead of being pointed at absent data; repointing is `rm` then `ln -s`, because `ln -sf` on a symlink-to-a-directory plants the new link *inside* the old target and `ln -sfn` is not POSIX; and `LAYOUT_CUSTOM` suppresses the default `$HOME` scan whenever any storage path is overridden, which is both principled and what keeps the test suite from repointing the developer's real projects.

One behaviour there is deliberate but easy to misread as a bug: **`--scan` replaces the `$HOME` scan, it does not extend it** (`_mg_scan=$_mg_roots`, and `$HOME` is only appended when no root was named). It falls out of `LAYOUT_CUSTOM` needing a single code path — an explicit root always means "look exactly here" — and `migrate` being idempotent makes a second run the fix. The suite cannot pin the additive alternative either: `run_mig` always sets the `CLAUDIO_*` paths, so `LAYOUT_CUSTOM` is 1 in every migration test and the `$HOME` branch is never taken. If you ever make it additive, the readme's "Which projects it looks at" paragraph is the prose that has to change with it.

## Traps — do not reintroduce

- **`$( )` and pipelines are subshells, so an `exit` inside one is swallowed.** The account is validated in `_run_prelude`, in the caller's shell, *before* `_build_env` runs inside `$( )`; otherwise Claude Code launches under the default login while reporting the requested one. `test.sh` guards this **behaviourally**: the unknown-account tests assert the exit code and the absence of `[claude]`, not just the error message, because asserting the message alone still passes if the launch happens anyway. The **exit code is the load-bearing assertion**, and the only one for `env` — "prints no `export` line" is vacuous, since `_build_env` validates before it emits anything, so that stays true whether or not the exit is swallowed. Verified by mutation: dropping both `_run_prelude`'s check and `|| exit 1` fails three tests. Note the two guards are independent — removing only one leaves behaviour unchanged, so `|| exit 1` is not redundant. Same reason for `component=$(_component_path …) || exit 1`.
- **An `else printf "(skipped …)"` over a file this repository owns is a guard that retires itself.** The packaging blocks were `if [ -f "$PKG_ROOT/Formula/claudio.rb" ]; then … else printf "  (skipped — no Formula/claudio.rb)\n"; fi`, and the else branch asserted nothing. Mutation-proven: with `Formula/claudio.rb` moved aside, `bash test.sh` reported **1171 tests, 1171 passed, exit 0** against 1179/1179 with it present — eight assertions (the whole dependency list, the `system "make", "install"` call, and the version `claudio update` parses out of a tap) gone in silence, on the run that is the release gate. The same shape as `usage/tests/test_all.py`'s floor guard, whose missing-file branch was an unconditional `check_true(..., True)`. A missing file that this repository owns is a **named failure**; a genuine environment fact — `command -v make` — is the only thing that may still skip.
- **A doc guard that greps a BLOB of every matching line asserts co-occurrence, not documentation.** The `account.<name>.ship_*` guard collected every line containing "global conf" into one string and grepped it for the bare key name, so the key and the phrase only had to appear *somewhere* in the same file with no relationship between them: one sentence naming both keys satisfied it single-handedly and the table rows were unguarded. Three mutations survived green, including a row rewritten to assert the exact opposite of the property. The guard now extracts the lines that name the key and requires the marker on **every** one of them, with the absence of any such line its own named failure — the shape the sibling `CLAUDIO_*` guard has always had (`sed -n 's/^| `\(CLAUDIO_[A-Z][A-Z_]*\)`.*/\1/p'`, "so a variable merely mentioned in prose does not count as documented").
- **A guard gated on its own extraction disables itself and prints a false reason.** The same block was wrapped in `if [ -n "$ship_keys" ]`, so an extraction that found the file and matched nothing was indistinguishable from a missing file: rewriting `conf.get("account.%s.ship_url" % name)` to string concatenation — a change with no behavioural effect at all — dropped fifteen assertions, printed "(skipped — usage/cu/ship.py not next to claudio)" about a file that was exactly where it said it was not, and exited 0 green. Gate on `[ -f ]` and nothing else, which is the only condition the skip message claims, and put the "the list was extracted" assertions **outside** the emptiness check, exactly where the `LOGGING_LEGACY` guard fifteen lines above has always had them.
- **`test.sh` runs under `set -e`:** a trailing `[ … ] && …` as the *last* statement of a function or `case` branch makes the whole command return non-zero. This has broken the suite twice — and had silently reappeared in the harness's own `fail()`, where it would have aborted the suite at the first failure that carried no detail message. Use an `if` block. **The same rule reaches any helper read by a bare `v=$(helper)`**, because the assignment's status *is* the substitution's: `recv_starts_seen` ended in `grep -c`, which exits 1 on a zero count, so the first real receiver regression did not fail three tests — it aborted the run and blacked out ~325 later ones (migrate, the statusline retrofit, update, both doc-drift guards). It survived only because a healthy tree never counts zero there. `|| :` fixes the status without touching the output, and the helper now has its own zero-count assertion.
- **`test.sh`'s `run()` must execute `claudio` with `$TEST_SH`, never a literal `sh`.** `$TEST_SH` is the shell running the suite, detected from `ps`. With a hardcoded `sh` — which is what it had — `dash test.sh` gave **zero** dash coverage of `claudio`: `/bin/sh` on macOS is bash 3.2, so the second run only re-exercised `test.sh` itself. Verified by injecting `arr=(a b)` into `claudio`: 335/335 green under both shells before the fix, a named failure under dash after it. The `claudio parses under <shell>` test and the `claudio under: <shell>` banner exist so this cannot rot silently again.
- **A redirected background command leaks the inherited stdout under dash, and the braces around it are load-bearing.** `_update_refresh >/dev/null 2>&1 &` looks detached and is not: dash saves the original descriptor to a high fd so it can restore it, and that copy survives into the child, so the pipe of any `out=$(claudio run …)` stays open and the **capture blocks until the refresh finishes** — measured at 3s against a deliberately slow `git`, with the child's output swallowed into `$out` as a bonus. bash does not do this, so `bash test.sh` alone shows nothing. Redirecting a *compound* command — `{ _update_refresh; } >/dev/null 2>&1 </dev/null &` — takes dash's other path and closes it; verified 0s under both shells, with the stamp still written after the parent has `exec`ed. The suite pins it with an elapsed-time assertion, which is the only shape that can catch it.
- **`$(( ))` over a value read from a file is fatal, not merely wrong, and digits are not enough to make it safe.** A leading zero is read as octal: `$((08))` exits dash outright and bash errors on it too, and `_recv_cap_ok` fed `recv.starts` straight into `$(( $2 - _rk_l ))` from the **main shell of `claudio run`**, where no trap catches it — one torn write or hand edit in a shared `usage_dir` killed the tool's primary verb with a raw shell error for an explanation, and its own comment claimed to have guarded exactly that. Compute the bound once from claudio's own numbers and compare with `test`, which parses base 10: that is what `_u_gt` already does, and it is safe over any digit-guarded string.
- **A data directory claudio cannot use must be said out loud, on every run.** `_recv_ensure` had two paths that returned 0 without a word — a failed `mkdir -p`, and a failed lock claim read unconditionally as "someone else is spawning", because the shell cannot see errno. With `otel=1` that meant telemetry enabled, claude launched, and every record posted to a closed port that Claude Code drops in silence, on the *first* run and every one after it; a `recv.lock` left behind as a regular file was unrecoverable without a manual `rm`, since `find -mmin` matches nothing that was never a directory and `rmdir` cannot remove a file. `_recv_cannot` is the single diagnostic, the lock claim now distinguishes EEXIST from "this directory is the problem", and both are pinned.
- **`shift` is a POSIX special built-in:** shifting past `$#` makes dash and ksh exit the whole script, so it is guarded (`cmd_mcp`) rather than relying on `||`.
- **POSIX sh has no scoping**, and `_ensure_profile_items` — plus `cmd_new`/`edit`/`show`/`init` — assigns a global `profile`. Anything that must survive a call into them is `RUN_`-prefixed.
- **`_parse_run_opts` returns `RUN_SHIFT`, a count**, rather than flattening the remaining arguments: flattening lost empty arguments, split on embedded newlines and glob-expanded on re-split. `_run_prelude` adds the profile name to that count, so `shift $RUN_SHIFT` still leaves `"$@"` byte-for-byte for `claude`. The `argv passthrough` section is what guards this, and it exists because the property was for a long time guarded by **nothing**: reintroducing the flattening (`RUN_REST="$*"` plus `set -- $RUN_REST`) left the whole suite green, and now fails ten assertions under both shells.
- **The launch shim must render argv, and how it renders it is load-bearing three times over.** `test.sh` builds its copy of `claudio` by replacing `exec claude` with `_fake_claude`, which prints one bracketed field per argument (`[claude] <-p> <hi>`). *No trailing `#`*: the old stub had one to suppress `"$@"`, but two of the three `exec claude` sites are `exec claude /login`, and the `#` commented the literal `/login` out — a harness that reports a plausible but false argv is worse than one that reports none, because the first login-path assertion pins a lie instead of failing. *`printf`, not `echo`*: dash's `echo` expands backslash escapes inside its arguments, so `a\nb` arrives as `a`+newline under dash and literally under bash — an argv assertion built on `echo` passes under one shell and fails under the other, the exact divergence `bash test.sh` alone cannot show. *One bracketed field per argument*: a space-joined list cannot distinguish an empty argument from an extra space, and empty arguments are one of the things being pinned. The definition is inserted as a single line after the real shebang, so the copy stays within one line of `claudio` itself.
- **An unescaped `[claude]` in an assertion is a bracket expression, not a literal.** `assert_contains` greps with `grep -q -e "$3"`, so `[claude]` matches any one of the characters `c`/`l`/`a`/`u`/`d`/`e` — it matched `profile: test-profile`, a string containing no launch at all, and that assertion sat vacuous for a long time. Every launch assertion writes `\[claude\]`; the one that did not is now an exact `argv` comparison, which cannot go vacuous.
- **`_validate_name` guards profile names as well as account names**, from exactly two places: `_require_profile` and `_new_profile_dir` (shared by `new` and `init`). `claudio new ../evil` used to create a sibling of the profiles dir, invisible to `list`. A leading dot is rejected for the same reason — `_dirnames` globs `*/`, so a dotted name could never be listed again. Deliberate consequence: `_require_profile` also sees names read from the `.claudio` marker, so a pre-existing marker holding a whitespace name now fails loudly on `run`.
- **Diagnostics on the `run`/`env` path go to stderr**, including `_require_profile`'s "Available:" hint — `cmd_env`'s stdout is meant to be `eval`'d.
- **`_resolve_account` prints `<source>\t<name>`**, not just the name: it runs inside `$( )` where a global would not survive, and reporting *where* the account came from is the point of the feature.
- **`host=` is emitted in the bottom tag layer**, so an explicit `--tag host=` or a config-file `tag=host=` still wins through `_merge_tags`. Its value is **sanitised, not validated**: `_validate_tag` rejects the spaces and commas that most real machine names contain, because `OTEL_RESOURCE_ATTRIBUTES` has no quoting. An unusable result omits the tag rather than emitting a bare `host=`.
- **`email=` is real PII and the docs must keep saying so.** It is the fourth automatic tag, read by `_dir_email` from the resolved account's `.claude.json`, and it exists because `account=` is only a label the user picked and anyone can overwrite with `--tag account=`. Two consequences the readme states plainly rather than burying: it lands in every exported record, and on a metrics backend it becomes a label, so one series per address. Three deliberate limits keep it defensible — it is emitted **only when an account resolves** (no `$HOME` fallback: the default login is not claudio's account to describe, and reading it would make the suite read the developer's real address and differ per machine); it sits in the **bottom** layer, so `--tag email=redacted` or `tag=email=…` in any config file suppresses it; and a value containing a space or comma is dropped, because it is parsed out of JSON with `sed` and `OTEL_RESOURCE_ATTRIBUTES` has no quoting. `_dir_email` uses `sed`, not `jq`, for the same reason `_settings_has_statusline` uses `grep`: a missing optional dependency must cost a label, never the command. `account list` shows the address only while the account is logged in — it survives in the file after a login is orphaned, and printing it then would imply a session that is not there.
- **`clean` removes only symlinks pointing into the profiles dir**, so it can never eat a file claudio does not manage. `_is_claudio_link`'s `*) return 1` is the whole guard: flipping it to `return 0` makes `clean` delete a user's own `CLAUDE.md -> ~/shared/CLAUDE.md`. The `clean` section pins all three unmanaged shapes (foreign symlink, regular file, directory) — that mutation used to leave the suite fully green. **`init` never captures `mcp.docker`** (it isn't in `CONFIG_MAP`), so a captured profile is always manual mode.
- **`_account_logged_in` greps `"oauthAccount"`** in the account's `.claude.json`: macOS keeps the credential in the Keychain, so the config dir carries only the marker. It delegates to `_dir_logged_in`, which takes a *directory* — `migrate` asks the same question about accounts that are not in `ACCOUNTS_DIR` yet.
- **A `$( )`-captured value has had its trailing newline stripped, and `read` discards a final line with no newline.** Feed such a value to a loop with `printf '%s\n'`, never `printf '%s'`. This silently dropped the last (often only) scanned project from `migrate`'s plan.
- **Storage paths are normalised with `_no_slash` at assignment.** Every symlink test is a literal prefix match on `readlink` output, so `CLAUDIO_PROFILES=/p/` built links under `/p/` and compared them against `/p//*`, matching nothing: `clean` reported success having removed nothing. `_no_slash` is defined above the assignments for this reason.
- **An empty directory prefix in a `case` pattern degenerates to `/*`, matching every absolute symlink on the machine.** `_links_under` guards emptiness *outside* the `case`, and `cmd_migrate` refuses to run at all if either profiles prefix resolved empty — otherwise a repoint pass would rewrite unrelated links such as a `.git/git-profile -> ~/.gitconfig.personal`.
- **Never conclude anything about durability from what the host sees through a bind mount.** Three documents carried a lesson that the OTel file exporter buffers ~4KB pages, does not flush on idle, and that `docker kill` silently discards the tail — so stopping the collector *had* to be `docker stop`. It is false, and it was reproduced wrong twice. Measured twice on 0.158.0: 5 OTLP records POSTed, host-side `wc -c` on the bind-mounted file read **0 bytes**, then `docker kill` (SIGKILL, no grace period) and `docker rm -f` — and the file held all 5 records, 3355 bytes. The zero was macOS VirtioFS bind-mount coherence lag: the host could not see bytes that were already durable. With `rotation:` configured the exporter writes through lumberjack, unbuffered per write. **No shutdown path is load-bearing for data integrity**, because there is no buffered tail. What a graceful stop still buys is narrower and must be stated as such: `uptime.jsonl` marks a span `clean` only on an *observed* graceful stop, and that label is what a server is told about which machines were listening — a **reporting** property, never an integrity one. Going native drops the bind mount, so the artefact cannot recur — and that is now done: `usage/recv/otlp-recv` is the receiver, spawned on demand, writing one `write(2)` to an `O_APPEND` file before it answers 200.

## Command surface — decisions with a reason

- **All profile items always exist** (live-link design). `_ensure_profile_items` fills blanks, and `edit` routes through it too, so a symlink always exists, a component created on demand is the same blank `use` would have written, and later additions take effect without re-activating.
- **`use` links and nothing else.** Any trailing argument is an error naming `run`. There is no launch flag: `use -l` used to `exec claude` without ever calling `_build_env`, i.e. with no account and no tags — a strictly worse `run`.
- **`new` never opens `$EDITOR`.** It used to open the profile *directory* unconditionally, wiping its own next-step hints and making the command unscriptable.
- **`account new` creates the dir and `exec`s `claude /login`.** An account with no login does nothing, so there is deliberately no create-only path; `login` is for re-authenticating.
- **`run` with no profile is a first-class case.** Ad-hoc directories get an account and tags with nothing written to disk — no marker, no symlinks — and the account is never recorded anywhere.
- **`clean` says when it removed nothing.** `_do_clean`'s loop is a subshell (`echo | while`), so the count cannot be a variable — `cmd_clean` captures its stdout instead. "Profile deactivated" printed over a directory of untouched symlinks is the silent-success failure the tool exists to avoid, and it is exactly what the `~/.claude` move produced.
- **`current` reports "nothing set" on stderr with exit 1**, matching `account default`, so `p=$(claudio current) || p=none` works. `clean`'s equivalent stays exit 0: it is an action, not a query.
- **`update` reports; it never installs.** Something owns the install — Homebrew, a distribution package, or `make install` from a checkout, quite possibly with `sudo` — so the honest move is to name that command (`brew upgrade claudio`, or the repo plus `cd claudio && sudo make install`) rather than rewrite a binary out from under a package manager. And there is no longer a single file to rewrite: `bin/claudio` without `libexec/claudio/` is a claudio whose two telemetry verbs cannot find themselves, which is exactly the install `make install` replaced. `--check` additionally writes nothing, not even the stamp. `--version` is a **flag, not a `version` verb**, so the usage doc-drift guard's verb list stays honest.
- **`_usage` lists Accounts above MCP servers**, and a test asserts the order — every other usage assertion is a contains-check and could not tell the difference. Accounts are what a new user needs second; MCP servers are what they need last.
- **`statusline` grew a flag, not a verb.** `--shim` is what settings.json runs and `--all` is the retrofit; both are options, so the usage doc-drift guard's verb list is untouched. The bare verb keeps its old meaning (the human report) and still exits 1 when nothing is set up — but "nothing" now means neither a renderer nor a `logging=` that records, because recording with no renderer is a legitimate silent sensor and reporting it as unconfigured would be a lie.
- **`show` and `edit` default to the active profile** at the dispatch table and share the same `[component]` argument. `show` prints one summary line per item; contents come from `show <profile> <component>`, so its output no longer grows with the user's data.

| `CLAUDIO_TAGS` | *(unset)* | Extra tags, comma separated `k=v,k=v`; beaten only by `--tag` |

| `CLAUDIO_USAGE_DIR` | `~/.claudio-usage` | The seam between the recorder and the reader. claudio exports it into the receiver so `usage_dir` and the receiver's data directory cannot disagree |
| `CLAUDIO_SELF` | *(set by `claudio usage`)* | The resolved path of the running claudio, handed to the Python half so `doctor` diagnoses it rather than whichever claudio is first on `$PATH` |
| `CLAUDIO_DOCKER` | `docker` | Docker binary for `docker mcp` calls (override for tests) |

| `CLAUDIO_REPO` | GitHub https clone URL | Repository the update check reads tags from |

| `EDITOR` | `vim` | Editor for `edit` and `mcp <profile> extra` |

Config-file keys (any of the three layers): `account`, `tag` (repeatable), `logging` (`none|local|remote`, default `none`), `otel_protocol` (default `http/json`), `otel_endpoint` (default `http://localhost:4318`), `usage_dir` (default `~/.claudio-usage` — **the path the `claudio usage` reader looks in**, so the default is a contract between the two tools, not a coincidence; changing it here means pointing the reader at the same directory).

Deprecated, read for one release and then deleted: `otel` (`1` to opt in) and `usage` (`1` to opt in to plan-usage recording), both replaced by `logging`. `LOGGING_LEGACY` at the top of `_logging_resolve` names them, and `test.sh` derives the list from that line rather than hardcoding a fourth copy.

**`otel_protocol` and `otel_endpoint` default to what claudio's own receiver serves: `http/json` and `http://localhost:4318`.** `recv/otlp-recv` is stdlib Python, so it speaks OTLP/HTTP JSON on 4318 and cannot speak gRPC on 4317 — HTTP/2 framing plus protobuf is not something `http.server` can be talked into. The defaults were the Docker collector's until the spawn work landed, which is exactly the handover that was planned: flipping them earlier would have pointed every existing export at a port that was now empty rather than one that merely might be, and leaving them afterwards meant the documented opt-in (`otel=1`) enabled telemetry, spawned nothing, and lost every record in silence. `claudio usage doctor` still compares claudio's actual export against the receiver's endpoint, because either key can be overridden in any of three layers.

Global-conf-only keys: `receiver` — the OTLP receiver `run` spawns and the shim keeps alive; `account.<name>.logging`, `account.<name>.otel_protocol`, `account.<name>.otel_endpoint` — per-account logging and destination, outranking every other layer (and, while they last, the deprecated `account.<name>.otel` / `account.<name>.usage`); `account.<name>.ship_url` and `account.<name>.ship_token` — where that account's records are shipped under `logging=remote`, and the tenant label sent with them, with **no plain-key form at any layer** and no default at all (see the shipper section: a machine-wide default destination would publish every account in one interleaved `usage_dir` to one server); `statusline` — the renderer the status line shim forwards to; and `update_check` (`1` enables the daily background check, `0` declines it permanently, unset means it has not been offered yet).
